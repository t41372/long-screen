## What was asked and what was done

The project was a Node/npm + Python codebase generated from `docs/original_requirements.md`. Two things were asked:

1. Convert it thoroughly to Deno.
2. Find out why every real screen recording in `test_case/` failed with `InvalidStateError: Failed to execute 'createImageBitmap' on 'Window': The image source is not usable`, producing only the first frame instead of a stitched canvas, and make the core algorithm properly tested against ground truth the model generates itself.

Both were done. Node, npm, TypeScript-as-a-dependency, and all Python test scripts are gone. The toolchain is Deno only: `deno bundle` builds, `Deno.serve` serves, `deno test` tests, Playwright is pulled through `npm:` specifiers for the browser suite only.

Nothing is committed. `git status` shows the whole tree as untracked; there are no commits in this repository at all, so there is no diff, no bisect and no way to verify any "it used to do X" claim in this document. Commit before you change anything.

This document was reviewed by a second agent against the tree, which found four wrong numbers and three imprecise claims; those are corrected here. Numbers age quickly: re-run `deno task coverage` and rebuild `dist/` before trusting any figure below.

## The real bug

There were two separate failures behind one symptom.

**The decode failure was a container-parsing bug.** ISO/IEC 14496-12 says the composition offsets in a `ctts` box are unsigned in version 0 and signed in version 1. Apple's ReplayKit writes *negative* offsets inside a **version 0** box. The demuxer followed the specification, read them unsigned, and produced presentation timestamps around 7,158,278 seconds. The decode loop saw time going backwards and aborted the whole recording. FFmpeg reads these offsets signed regardless of version; so does this code now (`src/media/mp4.ts`, the `ctts` and `trun` readers). Two fixtures lock the behaviour in: `negative-cts.mov` (version 1) and `negative-cts-v0.mov` (the same file with the version byte patched to 0, which is exactly the ReplayKit layout). `tests/unit/media.test.ts` asserts both produce an identical timeline, and asserts against the real recordings in `test_case/` when they are present.

**The `createImageBitmap` error was a separate UI problem.** The old UI read metadata and the first frame from a `<video>` element. When Chrome cannot render a container into a bitmap, that throws, and the app was stuck before it started. The worker now has a `probe` command that demuxes and decodes frame 0 through WebCodecs and transfers an `ImageBitmap` back, and that is the primary path. The `<video>` element is still loaded for every file, because compatibility mode and the "view the original moment" dialog need it, and it remains a metadata fallback if `probe` throws; what changed is that the app no longer *depends* on it to start. See `chooseFile` in `src/ui/main.ts` and `dispatch('probe')` in `src/worker.ts`.

Seven further defects surfaced while building the ground-truth tests. They are listed in `docs/TESTING.md` under 修正过的实际问题 with the reasoning for each fix.

## Read these too

`docs/CAPABILITIES.md` is the authoritative ledger of what works and what does not, mapped item by item onto the original requirements. It carries limitations this document does not repeat: no resumption from an interrupted frame, no general non-rigid reflow or infinite-scroll height change or virtualized lists, no arbitrary nested scroll containers (motion regions under 8% of the main layer are merged into their neighbour), no cross-zoom unified reconstruction, no guarantee that a whole page comes from one instant, and confidence scores that are heuristic rather than calibrated probabilities. `docs/ARCHITECTURE.md` explains the model and the reasoning behind each trade-off. `docs/FORMAT.md` documents the export format and every diagnostic code.

## The design decision that makes testing possible

Decoding is the only step that needs a browser. Everything after it is pure TypeScript:

- `FrameSource` yields `RGBA`, not an `OffscreenCanvas`. The `VideoFrame → RGBA` conversion is an injected function (`FrameConverter` in `src/media/source.ts`), so the decode loop's backpressure, ordering, stall and geometry-change branches are testable in Deno with a fake `VideoDecoder`.
- Analysis downscaling is an integer-factor box filter (`src/core/raster.ts`), not canvas resampling. Factor `f` means an analysis displacement times `f` is exactly a native displacement; the native refinement radius follows from `f`.
- Tiles are encoded and decoded by our own PNG codec (`src/codec/png.ts`), so bytes are identical in both runtimes and exports are still standard PNGs.

That means `deno task test` exercises the shipped code path, not a simulation of it. The browser suite covers what genuinely needs a browser: WebCodecs, the worker, IndexedDB, OPFS export and the UI.

## Ground truth, and what the tests actually assert

`src/synthetic/` generates procedural pages (`world.ts`), composes them into recordings with exact viewport paths, overlays and dynamic regions (`scenarios.ts`), and verifies a finished run against the generating world (`verify.ts`). Twenty of the scenarios are also offered in the app's demo menu, so the demo button runs material the test suite has verified.

Per moving layer the verifier computes: maximum placement error in native pixels, pixels observed but missing from the result, pixels present but outside every observed viewport, pixels whose value matches no content version at that coordinate and cannot be explained by an overlay, fragment count, and which diagnostics appeared. Fixed overlays are checked for pixel identity and zero conflicts. Unless a scenario declares otherwise, missing, invented and mismatched must all be **0** and max error must be **0**.

Three scenarios declare something different, deliberately, rather than being loosened:

- `repeated-list-reversal` — identical list rows, direction reversed mid-scroll. Moving up 15px and down 29px are pixel-identical when the row pitch is 44px. The assertion is that any error is a whole multiple of 44 and that the ambiguity is reported, not that the answer is right.
- `toolbar-collapse` — the address bar retracts and the content viewport grows. Marked a known limitation: the run must complete and report conflicts, with under 10% wrong pixels.
- `geometry-change` — the recording changes resolution part-way. It declares `status: 'partial'` and 20 rendered frames: the run must keep the decoded prefix and stop, not merge two pixel grids.

Everything else, including `blank` and `zoom`, is held to the full strict invariants. `blank` additionally has to report `UNOBSERVABLE_FRAME` and produce exactly one fragment.

23 scenarios plus an encoded-video `fixture` scenario. 189 Deno test cases in total (`deno task test`), the scenario runs included.

**A codec-dependent detail worth knowing.** Chrome's H.264 path returns pixels within about one level per channel of the source; its VP9 path returns them systematically darker (mean signed difference about −19 per channel, maximum 78). That is a colour-range conversion in the decoder, not a reconstruction error. The encoded-fixture tests therefore measure each codec's own decode floor first and require the reconstruction not to exceed it, instead of loosening the tolerance to whatever the worst codec needs. Geometry — placement error, missing, invented, fragments — is still asserted exactly for every codec.

`scripts/coverage.ts` gates on **line** coverage with a floor per file, each set to `floor(measured)` so a file can only improve. `deno task coverage --update-floors` rewrites the floor block from the run that just finished; review that diff, because a lowered floor hides a regression. Do not trust a green coverage run you have not seen the table for.

     0. **The comparison tolerance became a property of the SOURCE, not a constant** (`MediaInfo.noise` in `src/types.ts`, `DECODED_VIDEO_NOISE = 10` in `src/media/source.ts`, `Engine.noise`). Two decodings of the same source pixel are not bit-identical once the material has been through H.264 or VP9 — ringing and 4:2:0 chroma reconstruction move channels by several levels — so `PreciseSource`/`CompatibilitySource` declare 10 and keep exactly the threshold they always had. `ScenarioSource`/`DemoSource` are lossless and declare 0, so they are compared EXACTLY. Qualifying ring frames are sorted by displacement, the nearest TWO and the farthest one are always taken, and the remaining slots split the rest into equal bands taking the candidate with the FEWEST comparisons so far (`ConsistencyLayer.pairs`) in each. Displacement spread alone kept landing on the same anchor frames, so a frame whose only clean counterparts are in the FUTURE — content at the scroll's leading edge, which no past frame has reached — finished the run on two or three comparisons or none. Because a comparison scores BOTH frames and a frame is only finalised when it leaves the ring, a late pick counts in full. A ±1 disagreement says one of the two frames is wrong, never which; a disagreeing neighbour now fails to condemn this frame ONLY when the pixel has exactly one comparable neighbour AND voting independently found that neighbour inconsistent there. Two comparable neighbours keep the conservative reading.

Bit-identical, not a tolerance — a tolerance would also catch "genuinely different but close", which is what the block-conflict logic is there to protect.

## Things not to undo by accident

- `ctts` offsets are read **signed in both versions**. Making that spec-conformant re-breaks every iOS recording.
- Analysis downscaling must stay an **integer factor**. Non-integer factors reintroduce sub-pixel drift that accumulates over hundreds of frames.
- A stationary side band is only treated as fixed UI when it has visible structure of its own (`textured()` in `src/core/layers.ts`). Without that check, a page's blank margin is classified as a sidebar and the exported long screenshot loses its margins.
- Content entering at the leading edge has no counterpart in the previous frame, so a rival motion hypothesis "wins" there by default. `src/core/motion.ts` explicitly refuses to treat that as evidence of an independent layer. Removing it fragments every fast scroll.
- Thin-overlap steps (`THIN_OVERLAP_STEP`) get odometry weight 0.05 and can be overruled by revisit evidence (`TRAJECTORY_CORRECTED`). This is what fixes period-aliased fast jumps; the pose-graph weighting and the correction have to stay together, and the correction has to happen *before* `graph.add` so the odometry edge records corrected geometry.
- A cross-canvas loop-edge delta is the **raw pose difference**, `state.pose − keyframe.local` — it already carries the target canvas's attachment shift plus the revisit offset. Subtracting the attachment shift a second time when connecting the edge double-counts it and reintroduces the seam the attachment was supposed to close (`src/pipeline/engine.ts`, the comment above the `graph.connect(link.node, node.id, ...)` call).
- `ctts` stays signed in **both** box versions (see above); a version-0 box with negative offsets pushes a `NONSTANDARD_SIGNED_CTTS_V0`-prefixed message, which surfaces as a diagnostic with code `MEDIA_NOTICE` at severity `warning` (not its own diagnostic code, and not "informational" — it genuinely carries `warning` severity). The warning severity does not mean the file is broken; it only flags the non-conformant (QuickTime/ReplayKit) `ctts` encoding, which this code already reads correctly.
- `complete` on a `TemporalRegion` (`src/core/compositor.ts`) means "this observation rewrites every pixel of the block that was ever covered before," not "the block has 256 covered pixels." A block can be `complete` with partial coverage if partial coverage is all it ever had.
- Framing (`src/core/framing.ts`) must stay **O(perimeter tiles + observed source tiles)**. The cheap pre-check (grid arithmetic and a `Set` lookup, no pixel work) exists specifically so a large decorative background never forces a full bounding-box tile sweep; removing it turns a sparse frame into an accidental dense canvas.
- `MediaInfo.noise` is a property of the SOURCE and nothing else. Do not turn it into a setting, a per-scenario override or a similarity threshold: it answers "how far apart can two decodings of the same pixel be before the difference means anything?", which only the thing that produced the frames can answer. Lowering it for a decoded recording turns H.264 ringing into false flags on every frame; raising it for a lossless source re-hides the sub-threshold contamination this pass just made visible (a mean |ΔRGB| of 6 between a white glyph and a near-white page). Every comparison in the world-consistency mask, and the vote threshold via `CONSISTENCY_TAU`, derive from it — that single derivation is the point, so do not reintroduce a second independent constant.
- The ratchets in `src/synthetic/verify.ts`/scenario definitions (`maxMissing`/`maxInvented`/`maxMismatched`/`maxContaminated`/`maxContaminatedOverlay`/`maxContaminatedDynamic`/`maxContaminatedOverlayUnobservable`/`maxContaminatedOverlayRecoverable`/`maxProvisional`) may only go **down**. Raising one to make a run pass hides a regression instead of fixing it, and `maxContaminatedOverlayRecoverable` stays at its default 0 for every scenario that has no declared, traced reason otherwise — `dynamic` reaches 0 outright and asserts it. Ratchets have been raised exactly twice, both on explicit coordinator authorisation, both only after the residual was traced to a single mechanism, and both with that mechanism (with world pixels and frame numbers) written into the scenario's own comment: `toolbar-collapse`'s `maxProvisional` (21,115 → 42,759, where a provisional bit marks a pixel whose value is measurably CORRECT but which the engine can no longer certify once the viewport grows mid-recording), and `phone`/`chrome-everything`'s `maxContaminatedOverlayRecoverable` (0 → 1,759 / 2,001, where the only clean look at the world position is a boundary frame of the recording that the same pairwise disagreement condemns, and voting provably cannot have a verdict there). Neither is a licence for a third: a raise needs a mechanism, not a measurement.
- A provisional pixel (`Compositor`'s `provisional` bit, same layout as `coverage`) may be overwritten by a consistent observation **even inside a frozen block** — `frozen` protects a chosen moment from being re-picked, not transient screen-chrome burn-in (a cursor, FAB, scrollbar or toast the world-consistency mask flagged) from being fixed. Gating the heal path on `!frozen` like an ordinary replace would leave that burn-in permanent.
- A pixel the world-consistency mask could not check against ANY neighbouring frame (no prev, no next, or neither placement resolved to the same canvas) is consistent **by default**, not inconsistent. Content glimpsed in only one frame (the `glimpse` scenario) still has to be painted; treating "no evidence" as "reject" would turn every first/last frame and every short revisit into a hole instead of a guess.
- `Compositor.resolveTemporal`'s `maskComplete` check is deliberately all-or-nothing over an entire connected temporal-conflict component, not per-pixel — its own comment says so explicitly ("an observation containing a cursor/FAB is not a good 'complete moment' even when it is the first full view of this region"). This is a genuine, separately-designed invariant; do not relax it casually. It is NOT, however, what currently stands between `contaminatedOverlayRecoverable` and 0 on `phone`/`dynamic`/`chrome-everything` — that was checked directly (by instrumenting which block each traced pixel's healing frame actually went through) and ruled out; see item 6 above for the two mechanisms that were actually confirmed instead. Don't re-attribute future overlay-recoverable residuals to this gate without checking `conflictBlocks` membership for the specific pixel/frame in question first — the coordinate-mapping mistake that produced the original (wrong) attribution is an easy one to repeat: `render()`'s internal "world = screen + pose" is only equal to a scenario's own `layer.world` buffer coordinate when the region's viewport starts at screen (0,0); otherwise they differ by the viewport's own (x,y) offset, and `src/synthetic/verify.ts`'s ground truth always uses the latter (`layer.world`-buffer) convention.
- `solve()`'s consistency-voting local-search radius must scale with the analysis factor (`consistencyRadius = f`, not a fixed ±1). A fixed radius that worked at f=1/f=2 leaves a real, measured false-positive residual on `factor4` (f=4) alone, with no overlay or dynamic present at all — see item 6 above and `tests/unit/scenarios_d.test.ts`'s `retina`/`factor4` cases, which exist specifically to catch a regression here.
- `solve()`'s consistency-voting comparisons must stay restricted to INTERIOR cells (`consistencyInterior`): the cell and all eight of its blur taps in-region, and the whole ±`consistencyRadius` search window inside the box. `computeBoxGray`'s edge replication is right for the blur but makes a boundary cell's value something the partner frame — generally away from its own boundary, and therefore a plain 9-tap average — never computed; a clipped search window loses candidates on one side only. Neither bias cancels over partners, and at a leading edge, where a cell has two or three comparisons at most, they were measured producing a unanimous FALSE "inconsistent" verdict on `retina` with no overlay anywhere near the pixel. The mask is precomputed once per region (the box and the region mask are constant for a run), so this costs nothing per frame.
- `solve()`'s `consistencyPartners` must keep BOTH of its properties: the nearest two and the farthest qualifying ring frame are always taken, and the remaining slots pick the FEWEST-compared candidate (`ConsistencyLayer.pairs`) inside each equal displacement band. The spread defends against the coincidence quantified in the finalisation comment; the nearest-two rule is what lets a world position first seen at the scroll's LEADING EDGE be judged at all, because every qualifying partner for such a cell is a future frame and the two nearest ones overlap it most; the fairness term stops the same few anchor frames absorbing every comparison. Reverting any one of the three measurably regresses `phone`/`chrome-everything`. `performance.consistencyThinLayers` is the watchdog and must stay 0.
- `Engine.consistencyMask()`'s lone-neighbour excuse (a disagreeing neighbour does not condemn this frame when voting independently found THAT neighbour inconsistent at the same world position) applies only when the pixel has EXACTLY ONE comparable neighbour. Extending it to two was measured taking `chrome-everything` from 4.2k recoverable to 27k: an overlay taller than one frame's scroll routinely covers a world position in frames t and t−1 while t+1 is clean, and the plain any-disagreement rule is what catches that. Letting voting's POSITIVE verdict overrule a ±1 disagreement outright is worse still, for a different reason spelled out in item 6.
- `Compositor.add()`'s `identical === count` short-circuit must keep its `&& !provisionalInBlock` exception: a consistent observation with nothing to write still has provisional flags to clear, and skipping on identity alone left them standing for the whole run (measured: `retina` finished with 32 permanently provisional pixels holding perfectly correct values). Conversely the demotion rule below deliberately does NOT reach a block reproduced verbatim — an observation that repeats the whole block exactly is corroboration, not contradiction.
- `Compositor.add()` demotes an already-covered pixel to provisional when a REJECTED observation is **bit-identical** to it. This is what stops a screen overlay burning in on its first look at a world position (the look that paints it, before any flag exists). It must stay bit-identical, not a tolerance: a ≤10 tolerance also catches "genuinely different but close", which is exactly what the block-conflict logic protects, and `tests/unit/compositor.test.ts` pins both halves (the demotion, and that an inconsistent observation still never overwrites covered content).
- `src/synthetic/verify.ts` records an overlay's colours only where the composited frame DIFFERS from `RenderedFrame.beneath` (the same frame before any overlay drew into it). An overlay rect is a bounding box and some overlays paint only part of theirs, so recording the whole rect credited a screen overlay with page-space dynamic content it never touched — 252 of `dynamic`'s "overlay contamination" pixels were the animated widget's own background, seen through the mouse pointer's 10×16 box. Reverting this silently re-inflates `contaminatedOverlay` and mis-splits it against `contaminatedDynamic`.
- `solve()`'s consistency-voting comparison luma (`computeBoxGray`) must stay region-masked with edge-replicated taps at f>1, and must be gated OFF (raw per-pixel value, no blur at all) at f=1. It exists to suppress `downscaleGray`'s screen-fixed box-filter sub-cell-phase noise (real at f>1, measured with a temporary per-comparison diff histogram on `factor4`/`retina`; provably absent at f=1, where analysis IS native resolution). A plain region-UNAWARE blur leaks a neighbouring region's constant colour into this region's own boundary row; a naively-masked blur that just drops out-of-region taps under-smooths that same boundary instead of leaking into it, leaving a smaller but still nonzero residual; leaving the blur ON at f=1 introduces its own small boundary bias (a centre-weighted edge cell compared against an unweighted interior cell on the far side of a fractional pose delta). `tests/unit/scenarios_d.test.ts`'s `factor4`/`retina`/`fixture`/`geometry-change` (the last two are f=1, no overlay, no dynamics) are the regression tests for all of this at once — `provisionalPixels` must stay at 0 on every one of them.
- `solve()`'s voting record is THREE-state (`ConsistencyVote`: `bits` inconsistent, `clean` confidently consistent, neither = no verdict), and the third state is load-bearing, not bookkeeping. `consistencyMask()` asks a disagreeing neighbour "did voting find YOU inconsistent here?", and "not flagged" and "found clean" call for opposite answers; collapsing the record back to one bitset silently turns every unjudged cell into a trusted one. A positive verdict additionally needs ≥ `CONSISTENCY_VERDICT_MIN` (3) comparisons because it is used to override native-resolution evidence, while two unanimous disagreements are enough to merely flag (a flag can be healed later; a missed flag is permanent).
- `solve()`'s consistency-voting finalisation threshold is a RATIO, not literal unanimity: comparisons ∈ {2,3} still require every one to disagree, comparisons ≥4 only need a ≥75% net-disagreement supermajority (`consistencyThreshold(comparisons) = comparisons − 2×⌈comparisons×0.75⌉`). Literal unanimity (`comparisons === CONSISTENCY_PARTNERS && score === -CONSISTENCY_PARTNERS`) was the ORIGINAL design and is easy to reach for by instinct, but it has two real costs the ratio rule exists to fix: a frame with fewer than `CONSISTENCY_PARTNERS` qualifying ring partners (common near the start/end of a run, or on a canvas with few same-canvas frames) can never flag anything at all under literal unanimity, and a single coincidentally-agreeing partner blocks healing even when every other partner unanimously disagrees. Both rules share the same underlying risk (a persistent screen-fixed overlay makes roughly 1 in `CONSISTENCY_PARTNERS` spread partners coincidentally corrupt a genuinely clean pixel's comparison, proven with `tests/unit/consistency.test.ts`) — the ratio rule only tolerates it once `computeBoxGray`'s comparison-level fix above has already suppressed the OTHER, larger source of false disagreement (box-filter phase noise); reverting to a bare "≥2 comparisons, net score <0" majority WITHOUT that fix reintroduced far more false positives than it caught, confirmed by measurement before `computeBoxGray` existed.

## Running it

```sh
deno task start          # builds dist/ if missing, serves on 4173
deno task test           # unit + scenario end-to-end, no browser
deno task coverage       # the above plus line-coverage floors
deno task test:browser   # real Chrome: decode, reconstruct, UI, export
deno task fixtures       # regenerate encoded samples (needs ffmpeg)
deno task check          # type-check everything
```

The browser suite needs a real Google Chrome, not Playwright's bundled Chromium, which ships without H.264. Override with `LONGSCREEN_CHROME=/path/to/binary` or `LONGSCREEN_CHANNEL`.

`test_case/` is gitignored. Tests that need it skip cleanly when it is absent.

The browser harness rebuilds `dist/` whenever the bundle is older than anything under `src/` or `static/`, so the suite cannot quietly test a stale build. `deno task start` does the same only when `dist/` is missing, so run `deno task build` after editing if you are just serving.

`scripts/inspect-recording.ts` is a debugging aid: it streams a real recording through ffmpeg into the scan pass and prints the learned regions, per-frame motion and the row/column statistics behind the band edges. It is how the layer-detection problems on `c.mov` were diagnosed.
