# 2026-09 review 修复与性能记录

这是本轮已验证工作的记录，不代表原 review 的全部问题已解决。

## 已落实

- UUID：`randomUUID()` 缺失时用 `getRandomValues()` 生成 v4 ID；HTTP 不再阻止创建项目或导出暂存 ID。
- 能力判断：按实际 API 判断精确解码，不按 URL 协议一刀切；本机开发无需证书，区网 HTTP 可显式选择 native seek。
- Raster：统一整数 render pose；相邻观察各自取整再求差，排除已知邻帧 sticky occlusion。
- Analysis：CPU/WebGPU 保留非整除尺寸的尾部 partial cells；layer mask 使用一致的分析因子。
- 合成：比较实际 temporal block 集合；清除最后一个 provisional pixel 后恢复质量证据。
- 外框：映射 provisional/quality/conflict/owner/frozen；候选枚举不再扫描完整二维包围盒，超过限制提前退出。
- 导出：extent 使用绝对右/下边界，回归测试检查边缘像素而不只检查尺寸。
- 管线：缺失 scan/plan、自然提前 EOF、末批 journal 失败必须标记 partial；pending 与 dirty meta 在 commit 成功后才清除。
- 幀数语义：native seek 的计数是取样数，不沿用编码包数量；明确排除的 edit-list preroll 不算缺失观察。

## Profiling 方法与边界

`scripts/benchmark-pipeline.ts` 在 Chromium 中运行真实 WebCodecs、IndexedDB、三遍重建、framing、pyramid，保存 CDP `.cpuprofile` 和分阶段 JSON。它不是 Deno 中的模拟解码 benchmark，也没有测量 ZIP/PNG 导出阶段。视频与结果像素不发布到仓库。

```sh
LONGSCREEN_CHROME=/path/to/chrome deno run -A scripts/benchmark-pipeline.ts \
  --input recording.mov --passes 3 --output test-results/benchmark
# 可用 --baseline-root /path/to/old-checkout 对比指定旧版本。
deno run --allow-read scripts/benchmark-png.ts /path/to/old-checkout
deno run scripts/benchmark-consistency.ts
```

长时间量测每十秒记录进度到 `.progress.jsonl`。解码/执行失败也保存 `.failure.json` 和可取得的 CPU profile；
`--verify-tiles` 在计时与 profiling 结束后计算已提交 PNG 和全部 tile evidence 的 SHA-256，比较重复运行或 baseline/current，差异会使命令失败。

用户提供的 `e.mov` 实际探测为 H.264、3456×2234、936 个编码包、20.36 秒，不需要为 HEVC 转码。完整输入的尝试没有得到可用的完整结果；不能据此声称支持十分钟或 iPhone 真机规模。

为取得可检查的热图，用 ffmpeg **stream copy** 取前 60 个编码包，保持原生分辨率、码流和像素，不重编码。旧版最终交付 59 帧、却仍标记 complete（容器声明 60）；这正是必须保留 pass-count 诊断的理由。以下是该样本的探索性单次 profile，运行期间另一个旧量测程序仍在占用 CPU，**墙钟不能用作前后加速比或 release gate**：

| 阶段 | 墙钟 |
| --- | ---: |
| scan | 13.9 s |
| solve（含 optimize） | 17.8 s |
| render | 147.7 s |
| framing | 10.8 s |
| pyramid | 13.4 s |

重建阶段出现 2,761 次 tile decode、2,931 次 eviction，cache 上限仅 38 tiles。CPU profile 的主要 self-time 包括 `decodePNG` 22.2 s、`consistencyMask` 21.8 s、`Compositor.add` 9.8 s；PNG 路径确实值得先优化，但快取颠簸仍未解决。

第一项性能改动是 PNG 重建行循环：filter 按行分派而非逐字节判断、RGBA 整行复制、交换并重用两行缓冲。所有 filter/colour-type 测试保持 byte-exact，包括透明 RGB；没有降低质量、分辨率或放宽阈值。

独立 PNG 微基准（Deno 2.9.7，512×512 随机 RGBA，暖机后六轮、每轮 40 次，交错前后顺序）中位耗时 **13.50 → 10.69 ms/decode**，减少约 **20.8%**，约 **1.26×**。这是包含 inflate 的组件收益，**不是整条管线或 iPhone 的加速比**。浏览器 JS heap/CDP 数值也不是进程、GPU、decoder 的峰值 RSS。

## 第二批：consistency 与 tile cache

- `consistencyMask` 将邻帧 raster pose、有效 canvas 筛选和 native-to-analysis 坐标表移出逐像素循环，去除每像素邻帧数组与 occlusion callback；明确 condemned 后提前结束比较。没有改变 RGB 噪声门槛、投票规则或输出 mask。
- 用固定的旧循环检查 180 组随机输入的逐字节结果，并保留原有 consistency 场景测试。它是循环重构的等价性 oracle，不是独立的层分割/配准正确性 oracle。
- 原生 3456×2234 的独立 Deno 微基准，暖机后六轮交错测量：factor 6、noise 10、packed voting 与 occlusion 场景中位数 **587.54 → 452.60 ms**，约 **1.30×**；无损、无 voting 场景 **398.87 → 262.62 ms**，约 **1.52×**。不能外推成整条管线的倍数。
- Compositor 优先处理已在 cache 中的 tile，再载入冷 tile，避免画面 footprint 略大于 cache 时每一帧触发整轮 LRU miss。不扩大 cache、不提高内存预算。冲突 block 在 temporal 处理前恢复原始 raster 顺序。
- 固定 capacity 3、footprint 4 tiles、五次重复观察：decode **20 → 5**，eviction **21 → 6**。额外测试比较 `stable`/`latest`、负坐标、provisional、occlusion、跨 tile temporal conflicts 下的全部 PNG/evidence、索引、canvas 计数、诊断和 temporal rows。
- 补齐多张分页 PNG 的 fractional bounds 回归，检查右/下边缘实际像素和 32px overlap，而不只检查图片尺寸。

## 仍待处理

原 review 的临时数据规模、word posting chunk 化、真正原子的 tile/index/meta transaction、整体内存预算、两帧 packed consistency、并行 render、temporal/overlay 模型区分、parser fuzzing、独立 layer oracle 等仍需后续工作。时变 viewport、录制边界 overlay、重复内容反向 alias、断点续算也没有在本轮宣称解决。

Resident-first 缓解循环 LRU miss，不代表所有 cache churn 都已消失。Framing 的候选数上限也没有限制读取整个 source tile-index 的成本；presentation 的 observed/provisional 计数与 source-wide uncertain/conflict 累计值仍有统计口径差异。

Playwright WebKit 自动化不等于 iPhone Safari 真机。测试使用独立持久化 profile；该构建没有 OPFS 时验证明确的导出不可用提示，而不是假装导出成功。私密浏览模式下 IndexedDB Blob 支持仍有平台限制。
