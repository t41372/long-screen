# 模型、取舍与实现

## 一、问题不是累加 scrollY

合理的未知量至少包含：每层画布 C、每帧每层位姿 T、随时间变化的可见掩码 M、内容状态或版本 V，以及无法与其他部分建立关系的连通分量。观察是这些层在某时刻的组合，不是整页唯一静态图的无条件裁剪。

```text
I_t(u) ≈ compositing over layers k of M_(t,k)(u) · C_(k,V_t)(T_(t,k)(u))
```

本实现把可求解的主体限制为**分层平移** `T(u)=u+p`，把不符合该模型的证据放进诊断、时间冲突和独立分量。不是完整的动态场景生成模型。

纵向长截图是 x 位移接近零的特例；像素存储、位置图、区域判定和导出都不要求 y 单调。回滚不是删除或追加，而是再次观察同一坐标。

### 可辨识性不是多写几个 if 能消除的

完全相同的空白帧，可以来自暂停，也可以来自穿越白色区域。两张完全一样的列表卡片可以处于同一位置或相隔多个周期。没有重叠的两幅图不能仅由像素得出它们之间差多少距离。

因此“尽可能完整”不等于“一定只输出一个矩形”。多个独立片段加明确的未知关系，通常比一张错误接好的长图更有价值。测试套件把这一点写成断言：`repeated-list-reversal` 只要求误差是行高的整数倍并给出歧义警告，而不是要求答对。

## 二、为什么三遍

```text
第一遍  逐帧运动证据 + 全局运动区域学习      → 磁盘
第二遍  分层定位、原像素精修、历史重定位、位置图 → 磁盘
第三遍  按校正后的坐标做原分辨率瓦片合成
揭示    再解码四遍：认出浮在页面上的东西，把被它挡住或拼错时刻的块换成干净的一帧（§七「揭示」）
```

后面的回访约束可以修正前面的轨迹，同时不必把所有完整帧留在内存。代价是多次解码和多次磁盘访问，**不是实时处理承诺**。揭示的四遍只解码、不全量转换：每一遍只把它真要读的帧转成 RGBA，其余帧解码后直接关闭（§七）。

## 三、薄 TypeScript 外壳 + Rust/Wasm 核心

解码是唯一依赖浏览器 API 的一步（`FrameSource` 产出 `RGBA` 而不是 canvas，`VideoFrame → RGBA` 的转换是注入的函数）。配准、分层、位置图、合成、瓦片编解码、一致性投票等全部算法都在 `rust/long-screen` 的 `kernels` 与 `engine` 模块，编译成 WebAssembly；TypeScript 只做 UI、Worker RPC、浏览器 I/O（WebCodecs / IndexedDB / OPFS）与编排。迁移过程的历史记录见 [docs/history/2026-09-rust-migration-log.md](history/2026-09-rust-migration-log.md)（哪一轮做了什么，只记录过程，已完结，不再更新）；当前哪些模块在 Rust 里、哪些刻意留在 TypeScript 里，见下面§十一的代码地图与§十二的决策表，出现分歧以 `rust/long-screen/src/kernels/mod.rs`、`engine/mod.rs` 的 `mod` 列表与树本身为准。

核心以三种 Wasm 构建交付，`planCore()`（`src/core/wasm/loader.ts`）按运行环境能力选择：

- `core.wasm`（scalar）：没有 SIMD128 时的兜底。
- `core.simd.wasm`（SIMD128）：默认，SIMD128 可用、页面未跨源隔离或不满足线程条件时使用。
- `core.threads.wasm`（SIMD128 + 共享内存原子）：要求页面 `crossOriginIsolated`、支持 SIMD、有 `Worker`、逻辑 CPU ≥ 2；helper 线程数为 `min(CPU−1, 7)`。跨源隔离需要静态托管发送 `Cross-Origin-Opener-Policy: same-origin` 与 `Cross-Origin-Embedder-Policy: require-corp`（`static/_headers`，Cloudflare Pages / Netlify 支持；开发服务器 `deno task start` 也发这两个头）。不满足任一条件时退回 simd/scalar，原因写进 `COMPUTE_BACKEND` 诊断的 `detail.core` 并由 `CorePlan.reason` 报告，不是静默降级。
- Deno 测试默认加载 SIMD 构建；`LONGSCREEN_CORE=scalar|threads` 环境变量切换（`tests/support/core.ts`），线程数另有 `LONGSCREEN_THREADS`（默认 3）。构建产物在 `rust/target/{scalar,simd,threads}/wasm32-unknown-unknown/release/`，由 `bash scripts/build-core.sh` 生成（`deno task build:core`）；不要用裸 `cargo build`，`rust/.cargo/config.toml` 固定的是 scalar 的编译参数，裸构建会覆盖 SIMD 产物。

之前几轮迁移过程中的性能测量方法（A/B 基准 `benchmark-pipeline.ts --baseline-root`、`.baseline` git worktree 对照、`scripts/e2e-recordings.sh` 真实录屏基准）见 [测试说明](TESTING.md)。

- **分析缩图**是整数因子的盒式滤波（`analysisFactor` / `downscaleGray`，`rust/long-screen/src/kernels/raster.rs`），不是 canvas 重采样。因子 f 意味着分析位移 ×f 恰好是原像素位移，原像素精修半径随之取 `max(3, ⌈f/2⌉+1)`。
- **瓦片编解码**由 Rust 侧的 `image-rs` `png` crate 及其 deflate 后端驱动（两端字节一致），不是自制编解码器，导出的仍是标准 PNG。
- **区域归属**在扫描结束后一次性展开成原分辨率的 `RegionAtlas`（每像素一个字节），合成内层循环查表而不是调用函数。

Deno 测试与浏览器跑的是同一份 Wasm 核心（不像迁移前那样"同一份 TS 代码在两种环境里跑"），因此 Deno 里验证过的算法行为就是浏览器里的行为；浏览器测试负责解码、Worker、IndexedDB、OPFS 和界面这些核心之外的部分。

## 四、输入与解码

`BlobReader` 默认缓存 8 个 256KiB 页面，按范围读取头、样本表和媒体包，不调用整段输入的 `arrayBuffer()`。

MP4/MOV 解析普通 sample table 与 fragmented `trun`：DTS/CTS、sync sample、chunk offset、size table、旋转、简单编辑列表。**composition offset 始终按有符号读取**：ISO 14496-12 只规定 version 1 有符号，但 QuickTime / ReplayKit 在 version 0 的 `ctts` 里写负偏移，按无符号读会得到约 7,158,278 秒的时间戳并判定帧序倒退——这正是本项目最初对真实 iOS 录屏全部失败的原因。

WebCodecs 支持查询在启动前完成。按展示顺序消费输出、处理 B 帧、主动 `close()`；背压限制 decode queue、输出队列与在途请求。解码期的异常一律显式化，不静默：负时间戳帧按容器语义不展示但**计数并上报**；时间戳倒退时保留解码器顺序并上报，不再中止整段录屏；首帧尺寸与容器声明不符时以码流为准并上报，其后的尺寸变化保留前缀并报错。

扫描趟结束时拿处理到的帧数核对「期望帧数」（`MediaInfo.frameCount`，减去负时间戳跳过的帧），少了就报 `PASS_FRAME_COUNT_MISMATCH` 并把结果标为部分完成。期望帧数指解码器会交出的帧数，不是容器列出的样本数，两者在 iPhone 和 Mac 录屏上常差一帧：轨道唯一的编辑段结束处还列着一个样本（8 段公开录屏里有 5 段：test_4、test_6、test_7 的这个样本正好从编辑段终点开始，test_5 的在终点之后，test_8 的比终点早百分之一个时间刻度开始）。网页用 mediabunny 把每个样本都交给 WebCodecs，编辑表只用来平移时间，不在终点截断，所以网页的期望帧数就是 mediabunny 列出的包数，Chrome 与 WebKit 实际也解出这么多帧（test_6/7/8 为 336/406/599，状态完成，揭示照常运行，`test-results/frame-count/`）；终点之后的帧是屏幕的真实截取，照常保留（见 `docs/TESTING.md`）。原生解码器按编辑表截断：ffmpeg 把这个样本标成丢弃（`D`）、解而不出，AVFoundation 只交出展示时间落在编辑段 `[起点, 起点+时长)` 内的样本（精确比较，所以 test_8 的那一帧它照样交出，ffmpeg 把终点取整到整刻度后则不交出）。因此原生解码（`long_screen::decode`）的 `VideoInfo::frame_count` 是各后端自己会交出的帧数：ffmpeg 数 ffprobe 列出的未标丢弃的包，AVFoundation 用样本游标（`AVSampleCursor`）数落在唯一非空编辑段内的样本，Media Foundation 事先数不出，为 `None`。原生驱动照网页的方式用它核对。于是同一段录屏，网页比原生多分析编辑段终点那一帧（test_6/7 多一帧，test_8 网页与 AVFoundation 相同、比 ffmpeg 多一帧）。

解码帧转成 RGBA 在转换 worker 里做（`src/media/convert-worker.ts`），流水线线程同时处理上一帧，最多提前两帧。首帧用两种办法各转一次：WebGPU（`src/media/gpu-convert.ts`：按帧自身布局 `copyTo` 取出 Y 与色度平面，上传成纹理，着色器只做 YUV 矩阵，色度在每个像素中心双线性插值）和 `copyTo({ format: 'RGBA' })`。两者足够接近（与平面转换同一道闸门）而且 GPU 实测更快，才整段用 GPU，否则整段用 `copyTo`；一次运行只用一种转换，选定之后 GPU 出错就让这次运行失败，不中途换路。M5 Max 上的 Chrome 实测：3456×2234 的硬件解码帧 GPU 每帧约 4.3 ms，`copyTo(RGBA)` 约 16 ms，两者逐像素相差不超过 1 级（Chrome 对硬件解码帧的 `copyTo` 本身就是矩阵加双线性色度）。设置里的「仅 CPU」关掉这条路径；WebKit 的 Playwright 构建没有 WebGPU，照旧走平面转换。

## 五、运动候选与独立验证

分析图灰度化 → 平滑 → 空间均衡角点 → 256-bit BRIEF。匹配分为互为最近且有距离裕量的 distinctive matches 与显式保留的 ambiguous alternatives。二维位移直方图产生多个平移候选。

角点的 3×3 结构张量用三行滚动缓冲与 28 行评分带计算，选点顺序、同分顺序、ROI 与 BRIEF 描述子都与原来的整帧前缀和一致；中间缓冲从三张整帧 i64 积分图（`24×(W+1)×(H+1)` 字节）降到约 `260×W` 字节。

**局部描述子的唯一性不是页面位置的唯一性。** 定位阶段对每个候选做独立的重叠像素 audit：只看有纹理的像素，统计整体误差、明显不一致比例、真实重叠面积，以及 32×32 区块中有多少**与该位移一致**。区块统计把“页面整体按这个位移移动了，只有一个组件在变”与“这个对齐根本不对”区分开——前者是动画或懒加载，后者才是错误。

随后在**原像素**上精修并复核：`refineNative` 返回整数位移、残差和“离胜者两像素以外的最好残差”，后者小就说明存在周期性歧义；另有一个只给里程计救援用的截尾残差（胜者位移上最好的 75% 采样点的平均，见第十节）。候选排序带一个弱的匀速先验，用来在周期别名之间打破平局。取样点由 `select_native_points` 决定：把采样窗口按 `step × step` 网格分格，每格取一个点，而不是固定取格子角上的那个网格点。`track::odometry` 把这一步交给分析灰度图引导，按由粗到细两级选点：先在格子里选**分析尺度梯度最强的那个分析像素**（该像素对应的原生像素块与格子相交、块中心又通过掩码时才参与比较），再只在这一个分析像素对应的原生像素块内取**原生梯度最强的那个原生像素**（同级并列都取行主序中最先出现的）；格子里没有任何候选、或选中原生像素的梯度不超过阈值，该格不贡献点。没有引导（`refineNative` 的 ABI 入口、`ls_refine_native` 不带 `guide` 时）则退化为对整个格子做满分辨率扫描、直接取原生梯度最强的像素——引导以降采样因子 1 调用时，每个分析像素对应恰好一个原生像素，两条路径逐位相同。取样点只取决于当前帧、区域、掩码与引导，与具体候选位移无关，因此 `track::odometry` 对同一区域最多 6 个候选只选一次、复用给每次精修。

关键帧另存 24 块 32×32 的**原分辨率纹理片**（几 KB）。回访检索先用视觉词投票、再用分析尺度 audit 初筛，最后一律用这些纹理片在原像素上判定，因此重定位精度不受分析因子限制。检索到任何一个落在别处的合理解，就把这次回访标记为歧义而不使用。

位置图先尝试单锚点简单环的解析解：每个节点恰有两条对称、正有限权重的邻边，整图连通，沿环的闭合误差按边权倒数分配。所有二维残差都不超过 Huber 阈值 6 时才采用结果；其他拓扑和超阈值结果交回原有 Gauss–Seidel 求解，不改动回环测量本身。只有一条回环时 Gauss–Seidel 会在弱边上提前停下，这一步就是为它补的。

### 薄重叠的高速跳转

移动很快时只剩一小条重叠。在周期性排版里，相邻周期同样能解释这一小条像素，而且因为样本少，错误对齐的残差同样很低。这类步长被标记（`THIN_OVERLAP_STEP`），其里程计边在位置图中降权到 0.05；若随后的回访给出更强的原像素证据，整段轨迹被改正并记录 `TRAJECTORY_CORRECTED`，同时说明此前写入的像素保持原样、可能存在接缝。

## 六、分层

`LayerLearner` 在整段录屏上累计证据，而不是逐帧判断：相邻单元格的运动分歧、行/列切分增益、每行每列的时间变化量。

边界用**原生分辨率**的行列统计定位到像素，分析格只决定归属。四条静止带（上、下、左、右）都会被识别；左右两条看一列在多少帧里动过，所以整个窗口偶尔一起回弹不会让固定侧栏变成滚动内容。侧边带额外要求**自身有可见结构**：均匀的页面留白不会被当成侧栏，否则导出的长图会丢掉页面边距。两个 pane 之间的分隔条取最靠近切分位置的低变化列段。

前沿新进的内容在上一帧没有对应像素，任何竞争假设都会在那里“获胜”，这不是图层分裂的证据，已排除。面积不足最大内容层 8% 的小块运动区域并入最近的大区域：悬浮按钮旁边的一条缝不是嵌套滚动容器。

## 七、合成与时间冲突

合成不做跨帧透明度平均。像素有明确归属：未覆盖处写入，已覆盖处按分数决定是否整块替换。检测到冲突区域后，尽量选择一次**完整观察**整块保留或更新，并记录来源帧和时间；区域从未完整出现在一个视口里时保留诊断，不编造。这一条说的是移动画布；屏幕固定区域不挑时刻，每个像素取最后一次一致的观察（见下文「屏幕固定区域」）。

### 世界一致性掩码与瞬态像素

不随页面移动的屏幕坐标覆盖物（悬浮按钮、滚动条、鼠标指针、toast）如果被直接按世界坐标写入，会把自己烧录进移动画布——它们在屏幕上位置不变，但对应的世界坐标每帧都在变。渲染阶段用单帧前瞻消除这类烧录：`src/pipeline/render.ts` 的 `RenderPass` 把解码提前一帧缓冲（`pending`/`pendingPrev`），使合成第 t 帧时，第 t−1 帧的原生像素已经在手，第 t+1 帧也已解码完毕。对每个未跳过的移动区域观察，引擎的渲染会话（`rust/long-screen/src/engine/render.rs::RenderSession`，调用 Rust `consistency_mask`；`src/pipeline/consistency.ts` 的 `consistencyMask()` 是同一内核的独立入口，供 parity 测试与基准用）按屏幕像素比较"这一帧在世界坐标 W = 屏幕坐标 + pose(t) 处的内容"与"相邻帧（t−1、t+1）在同一世界坐标处的内容"——只在相邻帧对同一层的位置解析到同一张画布、且换算出的相邻帧屏幕坐标落在该帧和该区域的归属掩码内时才比较；比较用精确 RGB 相等作为快速路径，否则用平均绝对差 ≤ **本片源声明的解码噪声**（`MediaInfo.noise`，`Engine.noise` getter）判定一致。三帧像素放在会话自己的三槽帧环里，一帧只在某次放置第一次用到时装入；装新帧时只复用不属于正在合成的这一帧及其前后帧的槽，因为一次放置先拿到当前帧和前一帧的槽，再去装还缺的后一帧（§十）。

**比较容差是片源的属性，不是算法的常数。** 同一个世界像素在两帧里到底"一不一样"，取决于这些帧是怎么来的：H.264/VP9 的锐边振铃与 4:2:0 色度重建会让单个通道差出好几级，这与本项目做什么无关，所以解码视频（`PreciseSource`/`CompatibilitySource`）声明 `DECODED_VIDEO_NOISE = 10`，与一直以来的阈值完全相同；而合成场景与内置 demo（`ScenarioSource`/`DemoSource`）的像素是无损产生的，声明 0，于是**逐像素精确比较**。这不是把阈值调松或调紧，而是不再让无损片源替压缩视频的余量买单：一个画在 `[251,250,246]` 页面上的 `[255,255,255]` 悬浮按钮图标，平均 |ΔRGB| 只有 6，在 ≤10 的容差下与页面完全等同——`chrome-everything` 约 2,880 个、`dynamic` 全部 262 个残留污染像素就是这么来的，改用片源自己的噪声后它们才第一次被看见并修复。下面投票的阈值由同一个旋钮导出，整条流水线只有这一个可调量；本次运行用的是哪个值会写进 `MODEL_ASSUMPTIONS` 诊断的 `detail.noise`，因为"精确比较过"和"允许了 10 级余量"是两种不同的证据，事后从像素本身看不出来。

**±1 帧比较本质上是"成对不一致"信号：它只说明这两帧里有一帧是错的，不说明是哪一帧。** 因此判定规则是：只要有任一可比较的相邻帧不一致，本帧该像素即判为不一致——**唯一的例外**是该像素只有一个可比较的相邻帧（另一侧越界、不在同一画布或不在归属掩码内），且下面的环形投票**独立地**在同一世界位置判定那个邻居本身不一致：此时这次分歧归咎于邻居，本帧保持一致。没有这条例外，一段录制的最后一帧只要紧邻一帧被悬浮按钮遮住，自己也会被判不一致，于是再也没有任何观察能修复前一帧留下的瞬态像素（`phone` 世界像素 (335, 3217) 就是这个形状）。有两个可比较邻居时不适用这条例外——证据已经足够，宁可多标一个可被后续修复的瞬态像素，也不要漏掉一个永久烧录。完全没有可比较的相邻帧（例如整段录制的第一帧，或 `glimpse` 场景中只被扫过一次的内容）按一致处理——没有证据不等于证据说它错，孤例内容仍必须画出来。`consistencyMask()` 的注释里有完整真值表。

`Compositor.add()` 接收这份掩码（`consistent`，与 `labels`同尺寸、逐像素一字节），据此维护瓦片新增的 `provisional` 位图（与 `coverage` 同布局）：新像素总是写入，只是若不一致就顺带标记为瞬态；已覆盖且被标记瞬态的像素，只要新观察在该处一致就会被覆盖并清除标记——**不受该块的 `replace`/`frozen` 状态约束**，因为 `frozen` 防的是"重新挑选某个时刻"，不是"修复屏幕覆盖物留下的错误像素"；已覆盖且未被标记瞬态的像素，绝不会被判定为不一致的观察覆盖，即使块级 `replace` 满足也不行。

**被拒绝的观察如果与已覆盖像素逐位相同，会把那个像素降级为瞬态（只标记，不改写）。** 覆盖物第一次扫到某个世界位置时，往往正是"落笔"的那一帧：此时该像素还没被覆盖，而 ±1 帧比较要么在前沿没有可比较的邻居、要么因为邻居也在同一覆盖物下而"一致"，于是覆盖物被当成正常内容写下且不带瞬态标记；标记要等一两帧后才出现，那时写入已经被上一条规则挡住，错误就此永久烧录。既然被拒绝的观察在该处显示的正是已存的值，那个已存像素的证据强度不会高于刚被拒绝的这次观察，因此把它降级为瞬态、留给后续一致观察修复。判定用**逐位相等**，而不是上面那条按片源噪声取的容差：容差会把"内容确实不同但差别不大"也算进来，而那恰恰是块级冲突判定要保护的东西。

**整块逐位相同的观察会在更早一步被短路跳过**（`identical === count`），但这个短路现在要求该块没有未修复的瞬态位：一次一致观察即使无字可写，也仍然要清除它能清除的标记。反过来，一次完整复现整块内容的观察是**佐证**而非反证，所以上面那条降级规则刻意不在这里生效。块级 `replace` 只对"一致或默认一致"的像素生效。冲突检测本身（`TEMPORAL_OR_ALIGNMENT_CONFLICT`）仍然看到全部像素，不受这份掩码影响；但 `resolveTemporal()` 选择"完整时刻"整块覆盖时，要求候选观察在整个冲突分量的每个像素上都一致——包含鼠标指针的一帧不能被当成"完整时刻"。仍带有瞬态像素的块，质量分数会被封顶（`rust/long-screen/src/kernels/compositor.rs:526` 的 `t.quality[q].min(64)`），让质量遮罩能标出它们。`CanvasMeta.provisionalPixels`/`TilePayload.provisional` 记录当前仍未被修复的瞬态像素净数，会随后续观察涨落，不是单调递增的累计值。

页面坐标内的动态内容（动画组件、正在播放的视频、实时计数器）不受这套机制约束为零——它们允许保留某一个时刻的完整快照，只是同样会被世界一致性掩码判定为"不一致"（因为相邻帧的世界坐标处内容也在变化），因此也会带着瞬态标记，直到某次观察恰好与相邻帧一致才会被摘掉。

单帧前瞻并非在所有几何下都完全消除屏幕覆盖物：当覆盖物自身在屏幕上的尺寸大于相邻帧之间的页面滚动位移时（例如一个高度明显超过单帧滚动速度的滚动条滑块），该覆盖物中段像素在 t−1、t、t+1 三帧里换算出的世界坐标附近可能仍然全部落在覆盖物范围内，一次相邻帧比较无法把它和真实页面内容区分开——这是仅靠 ±1 帧比较这套方法本身的数学局限，不是实现缺陷。

**屏幕固定区域（固定栏、菜单栏、侧栏）用另一条规则：每个像素取它最后一次一致的观察，不挑时刻。** 固定区域每一帧都放在原点，所以"同一位置"就是相邻帧的同一个屏幕像素（`rust/long-screen/src/kernels/consistency.rs::fixed_mask`）。判定也反过来：只有与**每一个**可比较的相邻帧都不同（超出片源噪声）才判为不一致。扫过栏的指针、淡入过程中的每一帧都与前后两帧不同；淡入结束后的第一帧与前一帧不同、与后一帧相同，必须算一致，因为与它逐位相同的下一帧会被 `fixed_update` 当成"没变"跳过，按移动区域"任一邻居不一致即不一致"的规则，稳定下来的样子就永远写不进去。只有一个邻居而且不同（录制第一帧里有指针）判为不一致：照常写入、标为瞬态，下一次一致的观察修复它；没有邻居按一致处理。合成时固定区域的块不按分数替换，也不建时间冲突记录：每个一致的像素都覆盖已有内容（`Observation.latest`），不一致的像素不覆盖已覆盖的内容；冲突照样检测、照样报告 `TEMPORAL_OR_ALIGNMENT_CONFLICT`，但不再选"完整时刻"，所以固定画布没有 `frozen`，也没有 `INCOMPLETE_TEMPORAL_PATCH`。

原来固定区域与移动画布走同一套时间冲突记录，又没有一致性掩码，实测有三种失效。一、指针所在的那一帧被选成完整时刻并冻结；指针跳开超过一块，就开一条新记录，旧记录带着指针留下，成品里是一串指针（test_1、test_2、test_4、owner_1.53.20、owner_1.49.38 的菜单栏和工具栏画布，每个留下的指针都对得上那条记录最后一次写入时的指针位置）。块内指针占不到 16% 时不算冲突，指针的轮廓反而让清晰度分数高出 4–10，按分数替换后再没有干净的帧能换回来（test_1 顶栏 25 次替换里 13 次是这种）。二、macOS 菜单栏淡入、全屏 Chrome 外框下滑 64 px 时，每个冲突分量选中的是第一帧过渡状态（半暗的菜单字、撕开的地址栏、test_1 侧栏的"悬停框"）。三、test_2 的顶栏高 216 px，不是 16 的倍数，记录的矩形伸到 224，永远不算"完整可见"，3,024 块里 2,732 块停在第 0 帧，菜单栏是黑的。只给记录加掩码不够：记录在 ±16 px 内会合并，指针扫过留下的记录连成一整条，之后任何冲突都要求整条记录在同一帧里全部一致，而用户正是把指针移到屏幕顶部才唤出菜单栏的，这样的帧可能一直等不到。按像素取最后一次一致的观察，固定画布就是录制结束时栏稳定下来的样子；录制结束时指针停在栏里不动、或者某个菜单正开着，它们就是那个样子的一部分，会留下来，这是设计如此。每帧都在变的内容（转圈、视频）没有一帧与邻居相同，保留第一帧并标为瞬态。合成场景 `menu-bar` 与 `rust/long-screen/src/engine/render/fixed_tests.rs` 守着这三种失效。状态一直在变的区域另作处理：被学成固定区域、下面其实一直有页面内容滚过的区域（test_8 的半透明顶栏）没有哪一刻是「栏的样子」，取最后一个状态会留下录制结束时顶栏下面那块蓝色气泡。渲染会话为每个固定区域数有多少帧有块稳定到了新状态（冲突且整块一致）；多于两成的帧、且多于 10 帧时（test_8 顶栏 599 帧里 325 帧，真实录屏里的栏最多 1,258 帧里 83 帧），渲染结束时（`RenderSession::begin_finish`）这块画布改回第一帧，原样不动：栏下的内容在变，它在小片里的变化也不是栏上的瞬态。按块计数分不开这两类（test_2 顶栏有的块变过 10 次，test_8 顶栏的中位数是 14 次），按区域、按整段录制的比例才分得开。phone 场景右下角那块盖着滚动页面的固定区域达不到这个比例，仍取最后的状态。

**去掉瞬态的第一帧**（`rust/long-screen/src/kernels/fixed_history.rs`）。渲染会话为每个固定区域记下每个像素在第一帧的值，以及之后每一段相同取值（在片源噪声内）持续的帧数，直到区域第一次换状态：某一帧里稳定到新值（与相邻帧一致）的像素多于一个指针能盖住的范围（128×128，区域较小时取它的四分之一）。这第一段里一个像素持续最久的值，就是栏在那时的样子；它和第一帧不同的地方，第一帧显示的是瞬态，例如开头停在工具栏上的指针（test_2 的指针在前 8 帧都没动，一致性掩码认不出它）。这种差别只在指针大小的片里才采信：8 px 一格，相距 32 px 以内的差别连成一片，整片宽不超过 384 px、高不超过 128 px（指针连同它悬停的按钮：owner_1.53.20 第 0 帧里是 341 × 53，带着 Incognito 按钮的悬停样子）；这样的片连同周围 16 px 一起换成持续最久的值，指针柔和的阴影与底色只差几级，不在差别之内。成片的差别是栏下的内容在变（c 左侧区域里滚走的页头），第一帧原样保留。

### 位移展开一致性投票

为弥补 ±1 帧比较对"覆盖物尺寸超过单帧滚动速度"这类几何的失效，`solve()`（`src/pipeline/solve/solve.ts`）额外维护一份跨越更大时间跨度的证据：一个按分析分辨率保存的环形缓冲（`Ring`，`rust/long-screen/src/kernels/voting.rs`），每帧只保留各移动区域当时的画布 id / pose 与一份区域自有的、box 本地坐标系下的比较用灰度（`Ring::box_gray`，见下），按字节数定 budget（约 24MB，不保留原生分辨率帧）。对每个移动区域这一帧的最终 pose，从环里挑选最多 6 个满足"世界位移 ≥ Dmin"的历史帧作为参照——Dmin = max(64, 0.25×min(区域宽, 区域高)) 原生像素，取值刻意大于任何合理的覆盖物尺寸，同时远小于视口本身。

参照帧的挑法（`Ring::partners`）同时服务两件互相拉扯的事：

- **展开。** 合格候选按位移排序后，**最近的两个**、**最远的一个**总是入选，其余名额在剩下的区间里等分成若干段各取一个。每个候选本来就已经过了 Dmin，所以"覆盖物不可能同时在两帧的同一世界位置"这件事任何一个候选都成立；展开要防的是下面结算注释里量化的那个巧合——干净像素会和"位移恰好把该世界位置送进那一帧自己覆盖物范围"的参照帧不一致，而那是一个与覆盖物等宽的位移窗口。参照帧挤在一小段位移里就会整批落进或整批落出这个窗口，展开让这些巧合彼此独立。最近的两个是专门为**前沿**留的：一个世界位置刚进入视口时，能看见它的合格参照帧全部在未来，而未来帧里离它最近的那两个正是与它重叠最多的。
- **公平。** 每段之内选**已比较次数最少**（`Layer.pairs`，位移大者优先破平）的那一个。只按位移挑会反复挑中同几个锚点帧，于是"自己的干净对照只存在于未来帧里"的那些帧（滚动前沿上的内容，任何过去帧都还没到那里）几乎不会被任何未来帧选中，结算时只有两三次比较甚至一次都没有。由于每次比较同时给**两**帧记分（见 `Ring::compare`）、而一帧要离开环才结算，晚来的比较一样算数。`performance` 里的 `consistencyVotedLayers`/`consistencyThinLayers` 就是这条性质的看门指标：后者统计结算时比较次数不足以下任何正面结论的层，正常应当为 0（`tests/unit/consistency.test.ts` 有专门断言）。

比较只在**内点**格上进行（`RegionSlot.interior`，每区域算一次）：该格自身与 3×3 均值的全部取样格都在本区域内，且 ±`Ring.radius` 的局部搜索窗完整落在 box 内。两条排除都指向同一个实测失效——区域边界上的格会拿"邻居根本没有的值"去比较：`Ring::box_gray` 用中心格原值替换越界取样（边缘复制，对均值本身是对的），而参照帧对应的格通常不在它自己的边界上、用的是完整 9 点均值，两者因此差一个与内容相关、与覆盖物无关的偏置；被裁剪的搜索窗只在一侧少候选，偏向同一个方向。这些偏置不会在多个参照帧之间抵消，于是在**前沿**——那里一个格本来就只有两三次比较——足以凑出一次全票的假"不一致"，在 `retina` 上实测到（页面正常内容，附近根本没有覆盖物）。

每对比较落在分析分辨率的同一世界像素上（换算方式与 ±1 帧一致，只是坐标除以分析因子），用 ±`Ring.radius`（随分析因子缩放：`Ring.radius = f`）范围内的局部搜索取最小灰度差（阈值 `Ring.tau`，见下），容忍位姿在亚分析像素级别的残余误差和抖动，而不是要求恰好落在四舍五入后的同一格——这一层局部搜索是原生分辨率 ±1 帧比较不需要的（原生分辨率没有这种量化）。**比较用的灰度不是 `downscaleGray` 的原始输出，而是 `Ring::box_gray` 算出的区域自有 box 本地 3×3 均值**：`downscaleGray` 的取样网格固定在每帧的屏幕像素 (0,0)，不随世界内容移动，所以同一个世界像素在帧 T 与参照帧 S 里，只要两者的 pose 差不是分析因子的整数倍（几乎总是如此），就会落在网格里不同的"亚格相位"上——纯色内容不受影响，但 `factor4`/`retina` 这类精细边框/文字内容会因此产生真实但与覆盖物无关的灰度差，用临时逐比较直方图测得并确认（不是编造）。3×3 均值抹平这种取相位敏感的高频噪声，同时仍能清楚区分覆盖物；均值只取"同一区域"的相邻格（`regionContains` 过滤，越界或落在另一个区域/邻近固定覆盖物范围内的格改用中心格自身的原始值代替，而不是直接跳过不算）——直接跳过被排除的格会在区域自身边界上让均值样本变少、抹平力度减弱，留下比整体更小但依然非零的残留；直接不做区域过滤会让相邻固定区域的恒定颜色渗入区域自身的边界行/列（在 `fixture`/`geometry-change` 上实测到，被排除格全落在 box 的第一实际行）。**该均值只在 f>1 时计算；f=1（分析即原生分辨率）时直接使用原始值**——f=1 时不存在上述取样相位问题，均值反而会因为区域边界的不对称处理（当前帧的边界格用中心值加权、被比较帧对应位置一般不在其自身边界、用的是未加权均值）引入一个新的、内容梯度相关的小偏差，实测同样在 `fixture`/`geometry-change` 上出现且被 f=1 门控彻底消除。

投票的一致阈值 `Ring.tau` 由上面同一个旋钮导出，但多了一项 ±1 帧比较不需要的余量：`downscaleGray` 的取样网格固定在屏幕像素 (0,0)，所以 f>1 时同一个世界像素在两帧里落在不同的亚格相位上，这是**同一批无损像素的两个平均值之间**真实存在的差，算不到解码噪声头上，也不会因为片源无损而消失（`Ring::box_gray` 的 3×3 均值只是压低它）。因此 `Ring.tau = max(f === 1 ? 0 : phase, round(noise × 2.6))`，其中 `phase = 26`（该常量已内联进 `Ring::new`，不再具名，只在源码注释里留了 CONSISTENCY_PHASE 这个名字）是在 `factor4`/`retina`（都是无损片源）上实测的相位余量，且与均值本身同一个门控条件——只在 f>1 生效；f=1 时分析即原生分辨率，根本不存在相位项，无损片源于是同样精确比较。取 `max` 而不是相加，是为了让解码视频拿到的仍然精确是它一直以来的 26。

每次比较同时更新两侧（当前帧与参照帧）各自的净分数（一致 +1／不一致 −1）与比较次数，一帧离开环（或 `solve()` 结束）时才结算。结算阈值不是字面的"≥2 次比较、净分数 <0"，也不是要求与全部参照帧一致：比较次数为 2、3 时仍要求逐一致（⌈0.75×2⌉=2、⌈0.75×3⌉=3），比较次数 ≥4 时只需 ≥75% 的净不一致比例（`threshold(comparisons) = comparisons − 2×⌈comparisons×0.75⌉`）。要求全部一致曾经是必要的：一个持续存在、每帧都画在同一屏幕位置的覆盖物，会让"恰好有一两个参照帧的自身覆盖物位移窗口"碰巧落在被测世界坐标附近，从而让页面上完全干净的像素也偶然和某个参照帧不一致，简单多数会被这种巧合污染（`tests/unit/consistency.test.ts` 用专门构造的夹具证明并量化了这一点）；但全票要求本身也有代价——参照帧不足 6 个的帧（录制首尾附近，或同画布帧数少）永远无法标出任何东西，且哪怕只有一个参照帧碰巧一致，也会挡住其余 5 个一致同意的修复。上面的 3×3 均值把取相位噪声压低到足以改用比例阈值而不重新引入巧合误标——`factor4`（该均值机制的专门回归测试，见该场景注释）、`retina`、`tests/unit/consistency.test.ts` 均已验证。结算结果以分析分辨率位图形式写入 `consistency/<frame>`（见下一段的三态编码；只有当某个区域至少有一格拿到结论时才写这一行）。

结算写出的不再只是"不一致"一份位图，而是**三态**（`ConsistencyVote`）：`bits` 是判定不一致的格，`clean` 是以同一比例阈值的镜像（`score ≥ −`threshold`(comparisons)`，即 3/3、3/4、4/5、5/6 次一致）且比较次数 ≥3 的格，两者都不在的格**没有结论**（比较次数不足以判断，前沿和录制首尾的常态）。这个三分是必需的：上面 ±1 帧那条例外要问的是"那个邻居自己被判定为不一致了吗"，而"没被标出来"和"被判定为干净"要求完全相反的处理。正面结论要求 ≥3 次比较，因为它被用来推翻原生分辨率的直接证据；两次全票不一致足以引起怀疑（标记瞬态可以被后续修复），但不足以推翻直接证据。

渲染阶段读取 `consistency/<frame>` 以及**相邻两帧**的同一份记录（`rust/long-screen/src/engine/render.rs` 的 `VotingWindow`，用一个四槽滑动窗口把每帧三次查询摊成一次：会话用 `wanted_votes` 告诉宿主这一帧还缺哪几行，宿主读出来交给 `begin`），按分析因子放大到原生分辨率（原生像素所在的分析格不一致，则原生像素不一致）。投票判定不一致的像素直接不一致；否则走上面的 ±1 帧规则，而"只有一个可比较邻居"那条例外正是查邻居帧的这份记录。两套机制此后共享同一条 `Compositor.add()` / `provisional` 位图流水线。

每帧每区域的比较次数因此固定在 6 次以内（`voting::PARTNERS`），与录制长度无关。

即便如此，投票机制也不是万能的，且"检测到不一致"与"实际被修复"是两个不同的问题。`src/synthetic/verify.ts` 把每个 overlay 归因的污染像素精确拆成两类：`contaminatedOverlayUnobservable`（该世界位置在整段录制里**从未**被干净观察到过——比如页面从不发生水平滚动、覆盖物又逐帧无条件绘制在同一屏幕列，或悬浮按钮落在视口自身的滚动前沿、后续没有足够剩余视频让它移到未来某帧的前沿；这是场景本身的几何/素材属性，用与污染像素完全相同的算法在"该区域整段录制曾经可见的每一个世界像素"上重新计算一遍即可得到这个上限，与检测/修复机制无关）与 `contaminatedOverlayRecoverable`（该位置确实被干净观察到过至少一次，理论上应当被修复，目标是 0）。`dynamic` 已经达到目标（recoverable 与 contaminatedOverlay 都是 0，两个棘轮都是默认值 0）；投票之后 `phone` 1,675、`chrome-everything` 1,905 仍未达到；后面的揭示阶段再换掉一部分，剩 1,249 / 302，已经作为**已知局限**按实测值 +5% 显式声明（`maxContaminatedOverlayRecoverable` 1,311 / 317），因为投票留下的部分成因已经查到单一机制、可以逐像素复现：

**唯一剩下的机制是"唯一的干净观察正好是录制的边界帧"。** 残留里没有一个像素低于比较阈值（`phone` 全部是 |ΔRGB| ≈ 100 的滚动条灰与悬浮按钮橙；`chrome-everything` 只剩 194 个在 ≤10 以内），而且大多数**已经被正确标记为瞬态**（`phone` 1,675 里 1,240 个、`chrome-everything` 1,905 里 1,615 个）——缺的不是检测，是一次**有资格修复它们**的观察。形状永远相同：某个世界位置在录制只剩一两帧时才从滚动前沿进入视口，第一次落笔时正好被覆盖物盖住（该帧唯一可比较的邻居要么越界、要么同样在覆盖物下并与之"一致"），而唯一干净的那一帧是录制的**最后一帧**（或最前一帧），于是被同一次成对分歧一起判为不一致，失去修复资格。`consistencyMask()` 的"唯一邻居"例外正是为这种情况设计的，但它需要投票独立判定那个邻居不一致，而投票在录制边界上没有任何结论——一个在只剩一两帧时才进入视口的世界位置，在所有位移过 Dmin 的环形参照帧里都不在屏幕上，根本不可能产生任何一次比较。这是录制在哪里结束的属性，不是检测器的缺陷。实例：`phone` 世界像素 (382, 45)（帧 0–1，录制开头）、(335, 3217) 与 (387, 3072)（帧 62–64，录制结尾），`chrome-everything` 世界像素 (603, 2209)（帧 51–52，最后一帧）。

顺带排除了一个怀疑方向：`RegionSlot.interior` 排除在投票之外的边界格**不是**原因——`phone` 1,675 个残留里只有 2 个在每一个观察帧里都落在被排除的格上，`chrome-everything` 1,905 个里一个也没有。

已测得的残留数值、逐像素溯源，以及三个被实测否决、不要重新推导的方向，记录在 issue #2。

### 揭示：浮在页面上的东西

合成器保留每一块第一次写好的内容。浮在移动页面上的东西——聊天输入栏、悬浮按钮、滚动条滑块、半透明的淡入淡出遮罩——在它第一次出现的地方会被当成页面写进去；上面的 ±1 帧掩码对比滚动步长还大的覆盖物无能为力。随时间变化的页面内容（加载中的缩略图、展开的面板）则会在不同时刻写下的块之间撕开。揭示阶段在渲染之后、呈现之前补这两件事：整个阶段是引擎的 `RevealSession`（`rust/long-screen/src/engine/reveal.rs`：哪些决定算数、内存检查、喂合成器的瓦片、四遍的顺序、把选中的 16×16 块拷进瓦片），算法全部在 `rust/long-screen/src/kernels/reveal/`；`src/pipeline/reveal.ts` 是宿主（读行、解码、载入瓦片、存行）。它对每个移动层再解码四遍：

1. **学习**（`stats.rs`）：每个移动层按屏幕 2×2 格统计这一格和已渲染画布（按世界坐标对齐取格，奇数位姿不会跨半格比较）不一致的频率、观察亮度对参照亮度的回归，以及不一致时观察到的颜色。
2. **核对**（`model.rs`、`locate.rs`、`blocks.rs`）：由统计在 3×3 格池化后建模覆盖物——不一致比例高的是不透明物体；透光衰减要求亮度斜率置信上界与实际对比度都低于 0.85，即观察方差也低于参照方差乘以 0.85²。不透明替换本身可以有变化：接近零的斜率还须有对比度消失，或重复的可见不一致样本支持，不能要求所有替换都降低方差。只有协方差降低而对比度保留，可能是配准／取样误差，不能据此认定遮罩。不透明物体按连通分量分开，模板是不一致时颜色的均值。每一个投票帧里，不透明物体先在上次的位置找，再在附近 ±8 格找，最后沿两条轴整条找（有结构的模板用亮度数值一致及亮度归一化互相关，与学习时的稳定性定义一致；没有结构的模板仍要求 RGB 一致）；纯色物体（滚动条滑块）另在它的活动带内按颜色认格；竖条活动带左右紧邻的格子在这一帧里有一半以上也是这个颜色时，这个颜色就是页面自己的颜色，这一帧不按颜色认格。由此每个屏幕格得到一个洁净等级：干净、遮罩或没找到、边缘（不透明物体外两格）、不透明。每个世界 16×16 块按 8×8 格做逐格多数表决，只收最干净等级的视图，平票取较晚的视图；同时数出干净视图里与当前候选明显不同（平均差 > 8 或整体偏移 > 3）的次数。
3. **再学习**：同一套统计再做一遍，参照换成上一遍的共识。已渲染画布本身带着鬼影，只用第一遍时 f 的页脚就认不出来。
4. **写入**：一块只要有一次干净、与共识严格一致（没有任何亮度离群格）、离层边缘至少 48 px 的视图，就整块换成它；否则记住排名最好的视图（等级、严格一致、宽松一致、离边缘距离，平手取较晚的），到最后才决定写不写——更干净的观察与合成器原有像素一致时保留原像素；只靠一次干净视图形成的共识不算佐证，这样的边缘视图也只在比合成器原有像素更干净时才写。干净视图里至少两次、且至少四分之一与共识明显不同的块先组成相连的变动核心，再为各核心分配有观察支持、互不重叠的一格静态边界（初期低等级仍是已观察，不能被当成未观察；再学习可能提高其可靠性）；边界不会把无关核心合并。完整覆盖分量的时刻优先，再依不变边界是否矛盾、洁净等级、时间佐证、充分可见和时间先后排序。一个瞬态不能只因位置更靠中央而获选；新的内容得到佐证后仍会更新。尚无完整时刻的部分观察仍是 best effort，不能认证为完整 epoch。从未被完整干净看到的块逐像素取容差多数，只在更干净的观察与合成器像素矛盾的地方改写，同一块里与多数一致的像素也一并换成多数值，免得块内新旧混杂。对于初期只有较低等级共识的块，若后续两个完整干净的观察都确认整块及周围一圈没有结构，可以直接复制其中一个真实影格的整块；不以平均色填图，附近有细线或文字时不使用这个升级。

投票按「连续相同位姿的一段」计：一段只投一次，用这一段的最后一帧（最稳定的状态）。这一段最后两帧之间覆盖物活动区里仍在变化的格降为边缘——正在淡出的滚动条不能算干净。盲帧（纹理太少跟踪不到，求解沿用上一个位姿，合成器不画）一般不算进任何一段，只有一种例外：这一层所有跟踪到的帧都在同一个位姿上，盲帧沿用的也正是这个位姿，这时沿用的位姿一定对（`run.rs::admitted`）。b 右下角的悬浮按钮层只在鼠标指针经过时才跟踪得到（第 88–320 帧），不算盲帧时这一段在第 320 帧结束，那一帧指针还在层里，唯一的一票把指针烧进了成品；算上盲帧后这一段到第 369 帧才结束，指针没了，main 烧进去的滚动条也没了。覆盖物只在投票帧里定位，所以每一遍只需要把投票帧及其前一帧（统计遍是位姿变了的帧）转成 RGBA；`Reveal::wanted` 与 `Reveal::frame` 按同一规则判定，外壳据此让解码器跳过其余帧的转换（`FrameSource.sparseFrames`）。

整块从一帧拷来的块，瓦片的 `ownerFrame` 改成那一帧；每张画布另存一行 `reveal/<canvas>`，逐块记下像素来自哪一帧（整块拷贝的帧号、逐像素多数的 −2、保持合成器原样的 −1），供真实录屏的局部真值检查认证「这一片完整来自同一帧」（docs/TESTING.md、docs/FORMAT.md）。

### 弹性越界：页面边缘外露出的底色

macOS、iOS 的浏览器和看图应用在页面边缘允许内容越过边缘再弹回。跟踪如实跟着内容，所以这些帧的位姿越过了页面的边，区域里越界的那一条显示的是窗口底色（浏览器的灰色、页面自己的背景色、看图应用的黑色），不是页面。宿主在第一帧之前把全部 `plan/` 行交给渲染会话（`RenderSession::add_plan`）；第一次放置运动区域时，会话把每张画布上的全部放置按最终位姿（经位置图改正和接回位移，取合成器用的取整位姿）排成轨迹，对四条边分别求出页面的边（`rust/long-screen/src/kernels/overscroll.rs::page_edges`，会话一侧在 `rust/long-screen/src/engine/overscroll.rs`）：

1. 一次「回弹」是越过某个值的一段帧：从页面一侧进入，以小步回到这个值（最后三次回程都不超过 5 px），然后停住或再往外走；越过至少 2 px、至多区域该方向尺寸的四分之一。回到之后又在原处停两帧算「停稳」。
2. 边在最外侧那组停稳的回弹附近（相距 3 px 内算一组，组里的回弹数至少是最大一组的四分之一）。没有停稳的回弹时用全部回弹；如果页面从没在那附近停留过（不到 8 帧），说明弹簧还没回到原位就被用户滚走了，边改取回弹内侧、四分之一范围内页面停留过 8 帧以上的最外侧位置。
3. 在这组附近，取页面停留帧数最多的那个值：按住越过边缘时只停一会儿，停在边上的时间长得多。
4. 任何一帧越过这个值超过四分之一，这一侧就不算有边：页面在那边还有内容。

只凭运动分不清弹回和录到范围最外侧的一次普通往回滚，所以每一帧还要看像素：越过边缘的那一侧，从区域外沿往里数「底色行」（`background_lines`）——一行里 95% 的像素与这一行的中位色相差不超过片源噪声（剩下的 5% 容得下指针尖和滚动条滑块的边）。数到第一行有页面内容的地方为止。只有把钉在屏幕上的像素（与相邻帧同一屏幕位置相同，而相邻帧的位姿不同）放到一边才是一个颜色的行，最多连续 32 行、且后面还接着底色行时照样计入：这是贴着视口边的细条（test_5 的下边）；更长的一段、或者数到头还没完的一段就停下，钉在底色上的按钮、被区域学习留在运动层里的侧栏都当内容看。最多数到越界量。数到的行离越界量不超过 3 行（运动读出的边可能比底色真正的尽头靠外一两个像素），这些行才作为遮挡矩形加进这次放置；差得更多说明那一条里还有别的东西——页面内容，或者钉在运动层里的输入框——整条照常合成，页面内容因此永远不会被留空。只留空外面一截不行：test_8 的越界帧会把运动层里的输入框画到一个个错开的位置，页面底端被撕碎。遮挡矩形走现成的路：合成器、时间记录的完整性检查和揭示都不看被遮挡的像素，观察台账行带着它们，画布范围（`CanvasMeta.bounds`）也不含它们。重复帧捷径不重新测量，沿用同一层上次在同一位姿上的结果。宿主不交 plan 时，渲染与以前完全一样。

## 八、输出

原尺寸磁盘瓦片 + 覆盖位图 + 有限 LRU 缓存。查看器只绘制可见区域，预览金字塔按 alpha 加权减半，不让未观察像素把已观察像素拉暗，且不改写 level 0。

导出：完整项目 ZIP64（原尺寸瓦片、离线查看器、覆盖与质量信息、逐帧记录、位置图、诊断），或当前画布 PNG / 二维分页（流式编码，超尺寸时分页并记录坐标与重叠，不静默缩小）。未观察像素保持透明。

## 九、明确没有做的

- 通用非刚性 reflow、任意嵌套滚动、跨 zoom 的统一重建。检测到比例变化时保留独立片段并报告倍率，不缩放混合。
- 语义识别（视频播放器、弹窗、sticky 元素）。处理的是视觉变化区域。
- 断点续算。可以恢复已提交结果，不能从中断帧继续计算。

Rust/Wasm 核心（scalar/SIMD128/threads 三种构建，见 §三）、WebGPU 分析加速与第三遍重复帧跳过都已实现，不在上面这份清单里：

`AnalysisComputer`（`src/core/compute.ts`）用一个 WGSL compute shader 做盒式滤波降采样（灰度 luma + 整数因子降采样），只加速 `gray()` 这一步；特征匹配、位置图求解、像素合成全部保持 CPU 算法不变。`auto` 模式在第一帧同时跑 CPU 与 GPU 路径，要求逐字节位精确（`bitExact`）且 GPU 实测（含上传、kernel、回读）比 CPU 快，否则整段运行退回 CPU；适配器缺失、分配失败、设备丢失、超时都通过同一个回退路径保留观察，不是静默降质。`explicit webgpu` 模式跳过速度比较但仍要求首帧位精确。校准结果记录在 `performance.json` 的 `compute` 字段。`Params` uniform 缓冲区必须按 WGSL 的 16 字节 struct 对齐分配（五个 u32 仍要凑够 32 字节），否则 Chrome/Dawn 会按这个最小绑定尺寸校验并拒绝——Deno 自带的 wgpu 曾经并不校验，这个差异一度让该问题只在真实 Chrome 里现形。

扫描会话（`rust/long-screen/src/engine/scan.rs::ScanSession`）对逐字节相同的连续帧（RGBA 逐字节比较，不是感知相似）跳过重复的运动估计：复用上一帧的运动场与特征，`performance.json` 的 `exactDuplicateFrames` 记录跳过次数。这只影响扫描阶段的重复工作，不改变输出像素或覆盖集合。

### 混合坐标系的位置图与接回几何

位置图里的每个节点活在**它自己画布的坐标系**里，不是一个全局统一坐标系：一个独立片段被回访证据接回主画布之前，它的节点坐标是片段自己的局部坐标；接回之后，新产生的节点才直接是目标画布坐标。跨画布的回环边（loop edge）记录的是**原始位姿差**——`state.pose − keyframe.local`——这个差值本身已经包含了目标画布的接回位移（`Attachment.dx/dy`）与本次重访的 offset，因此连接图时不能再减一次接回位移，否则会被减两次。渲染阶段反过来：从一个片段画布出发，如果它已被接回，渲染位移要把 `Attachment.dx/dy`（测量时相对目标关键帧节点的刚性位移）再加上该目标锚点节点自己经过全局优化后的 correction（`attachedRenderShift`），因为接回之后目标画布自身的节点还会因为后续的里程计/回环边继续移动，片段必须跟着走，而不是冻结在接回瞬间的位置。

### 长基线图层学习

`LayerLearner` 不止看相邻帧：当逐帧位移小于一个分析像素时（例如极慢的滚动），单帧证据不够可靠地把固定栏和内容区分开。除了逐帧证据，学习器还累计帧 t−k 与帧 t 之间的长基线比较——只有累计位移足够大时才纳入统计——这样慢速滚动仍能积累出可用的行/列切分增益，而不必等到运动本身变快。逐帧与长基线证据共享同一套判定阈值，不是两套独立标准。

## 十、不要误改的不变式

下面每一条都对应一次实测到的失效，改动前请先确认自己知道它为什么在那里。§七 对其中一致性相关的几条有完整推导，这里只给结论与出处。

### 解码

- **`ctts` 偏移在两个版本里都按有符号读取**（容器解析已交给 npm 包 mediabunny，它本身就这样读；本项目只在 `src/media/isobmff-probe.ts` 里加了一个轻量探测，专门用来在版本 0 出现负偏移时补上 mediabunny 没有的诊断）。版本 0 的负偏移会推送 `NONSTANDARD_SIGNED_CTTS_V0` 消息，以 `MEDIA_NOTICE` 码、`warning` 级别呈现；这个级别只标记非规范（QuickTime/ReplayKit）编码，不表示文件坏了。
- **帧转换只做 YUV 矩阵，不做色彩管理。** 把解码帧作为 WebGPU external texture 导入更快（3456×2234 每帧约 1.5 ms），但浏览器会把 BT.709 的传递函数换算到 sRGB，照片中间调整体亮出约 10 级（0 的缩略图与原生帧的平均差从 2.1 变成 10.4），而且这一点亮度差足以改变区域学习与跟踪的结论：c、0-1、b、e 的画布切分都变了。屏幕录像的像素本来就来自 sRGB 屏幕，`gpu-convert.ts` 因此自己上传平面、自己做矩阵。
- **期望帧数是解码器会交出的帧数，不是容器列出的样本数**（§四）。原生命令行原来用 ffprobe 的 `nb_frames`（容器样本数）作期望，ffmpeg 解码时 test_4 到 test_8 五段录屏全部以 `PASS_FRAME_COUNT_MISMATCH` 结束为部分完成（如 test_6 只处理 335/336 帧），揭示阶段也随之跳过；AVFoundation 则不给期望，真正少了帧也发现不了。网页的期望（mediabunny 的包数）与它交给 WebCodecs 的一致，不要改成按编辑表截断；原生各后端的期望由解码模块（`long_screen::decode`）按自己的截断方式数（`test-results/frame-count/`）。
- **GPU 转换在转换 worker 里做，不在流水线线程上。** 放在流水线线程上时，平面拷贝、纹理上传和回读拷贝都压在关键路径上，f 的扫描与渲染反而比 worker 里的 `copyTo` 慢（2.9 对 2.8 s、4.3 对 3.6 s）；挪进 worker 后是 2.0 s 与 3.2 s。

### 几何与分层

- **分析降采样必须保持整数因子**（`src/core/raster.ts` 转发到 `rust/long-screen/src/kernels/raster.rs`）。非整数因子会重新引入亚像素漂移，在几百帧上累积。
- **静止的侧边带只有在自身具备可见结构时才算固定 UI**（`stationaryBoundary`，`src/core/layers.ts` 转发到 `rust/long-screen/src/kernels/chrome.rs::stationary_boundary`）。去掉这个检查，页面的空白边距会被判成侧栏，导出的长截图就少了边距。
- **左右静止带看一列在多少帧里动过，不看它的平均变化量**（`rust/long-screen/src/kernels/regions/bands.rs::STATIONARY_COLUMN_SHARE`，累加器 `rust/long-screen/src/kernels/layers.rs` 的 `col_moving`）。页面滚到底时，macOS 的弹性回弹会把整个窗口连同固定侧栏一起挪动几帧：g.mov 的 479 个有效帧里有 20 帧这样，侧栏的平均变化因此超过 0.7，被当成滚动内容，整条侧栏被抹进长画布；按「动过的帧占多少」算，侧栏不到 0.05，滚动内容远高于 0.25。其余九段真实录屏的左右边界在两种算法下逐列相同。平均变化量 `col_change` 仍然用于两个 pane 之间的分隔条和画布裁边，上下静止带也仍按行的平均变化判断（各录屏都不需要改）。
- **静止列一路走到 45% 上限时，仍在上限以内找侧栏自己的边**（`rust/long-screen/src/kernels/regions/bands.rs::detect_bands`）。侧栏旁边空白的页面边距同样一动不动，从窗口边缘往里走的静止列会穿过它：test_2 里浏览器的标签栏和 ChatGPT 的侧栏旁边是对话区空着的深色边距，一直走到 x 1584，超过了 45% 的上限，以前整条左侧带就此作废，侧栏留在移动层里，撕成合成器拼出来的碎块。现在走到上限也照样用 `stationary_boundary` 在上限以内找最后一条贯穿上下的边（test_2 是侧栏右缘 x 1000），找到了再交给「自身有可见结构」那条检查决定算不算侧栏，所以空白边距仍然不会被当成侧栏。右侧同理。
- **前沿新进的内容不算图层分裂的证据**（`src/core/motion.ts` 转发到 `rust/long-screen/src/kernels/motion.rs`）。它在上一帧没有对应像素，任何竞争假设都会在那里默认「获胜」。移除这条会让每一次快速滚动都碎成片段。
- **薄重叠步长（`THIN_OVERLAP_STEP`）的里程计边降权到 0.05，且回访改正必须发生在 `graph.add` 之前**（位置图的节点、边与回环分摊在 `rust/long-screen/src/engine/pose_graph.rs`，`src/core/pose-graph.ts` 只按原顺序读写 KV；Gauss-Seidel 松弛本身在 `rust/long-screen/src/kernels/pose_graph.rs`，见十二节），这样里程计边记录的才是改正后的几何。降权与改正是一套，拆开任何一半都会让周期别名的快速跳转重新错位。
- **跨画布回环边的 delta 是原始位姿差** `state.pose − keyframe.local`，它已经包含目标画布的接回位移。连接边时再减一次会双重计算，重新打开接回本应闭合的接缝（见 §九「混合坐标系的位置图与接回几何」）。
- **原生精修按格取点，不是网格点本身**（`rust/long-screen/src/kernels/motion.rs::select_native_points`）。取网格点只在节点像素恰好落在边缘上时才采到样：稀疏的暗色页面上，边缘处处不在节点上，`< 12` 个样本触发 `Infinity`，真实步长被当成「静止」丢弃（`e.mov` 实测约 1600 个节点里只留 9–11 个）；与此相反，一条与网格行/列对齐的屏幕固定线（悬浮滚动条）则会在该行/列的每个节点上都被采到，其残差压过其余页面内容，导致真实位移被拒绝或被误差更低的周期别名取代（`d.mov`/`e.mov` 实测：水平滚动条正好落在某一网格行，46 个样本里 22 个来自这一行）。`track::odometry` 用分析灰度图由粗到细选点（格内先选分析尺度梯度最强的分析像素，再在它对应的原生像素块内选原生梯度最强的原生像素）而不是对整个格子做满分辨率扫描——降采样因子越大，每格要扫的原生像素就越少；因子为 1 时两条路径逐位相同，这一点由专门的回归测试和奇偶校验测试守护。
- **没有一个假设有 4 个匹配时，取匹配最多的两个（各 3 个）照样在原生像素上精修，由原生判据决定**（`rust/long-screen/src/kernels/track/odometry.rs::FEW_MATCH_MODELS`）。暗而稀疏的一帧只有几个特征，若真实的那一步只得到 3 个匹配，它连精修都进不去，这一帧落到差异采样：空白像素压低了平均差异，于是被判成「静止」，位姿不动，之后每一帧都继承漏掉的这一步。实测失败：test_4（HDR 录屏里的一幅油画）第 1080 帧只有 4 个匹配，真实的 112 px 一步是唯一的假设、只有 3 个匹配，平均差异 0.603 < 5，被判静止；此后每帧都偏 111 px，嘴、眉毛和画框顶部出现接缝，回访拒绝了 36 次闭环。改后这一步的原生残差 2.2、次优 5.2，按跟踪处理，第 1080 帧落在 4328（独立配准为 4329），被拒的闭环为 0，接缝消失。只有没有任何假设达到 4 个匹配时才用这两个候选，其余帧的候选集合和最多 6 个精修的截断都不变：20 段真实录屏里只有 test_4 和 test_5 各有一帧走到这一步，test_5 那一帧两个候选都没通过审核，输出不变；合成场景的指纹逐行相同。
- **原生残差超过 14 的一步，只在本来要开新片段、且比例上明确时才救回**（`rust/long-screen/src/kernels/track/odometry.rs::rescuable`，`rust/long-screen/src/engine/solve/region.rs::apply_lost`）：残差平均值仍是判据；被它拒绝的一步照旧先走重新捕获锚点和关键帧重定位（重新捕获与这一步矛盾时除外，见下面第二条），两者都失败、本来要开新片段时，若这一步相邻位移明显更差（次优残差 > 1.5 × 残差）、且去掉最差 25% 采样点后的截尾残差只占次优残差的一小部分（< 0.35 ×），就按这一步跟上，保留原残差，置信度低、标为不确定。所以凡是今天能放好的帧一律照旧，只有原本要碎成新片段的帧会变。这些阈值都是比例，因为残差随内容对比度成比例变化：HDR 录屏换成正确颜色后，同样的一步残差约是原来暗色显示时的两倍，而固定阈值 14 原本只是刚好够用。实测失败：带 HDR 屏的 Mac 录屏（g）里不随页面滚动的侧栏、iPhone 录屏（iOS 26）里半透明的底部标签栏，都被区域学习算进了滚动层，它们的采样点把平均残差推到 14.3、14.9，快速甩动时到 18–26；颜色正确后 g 碎成 88 个片段、iPhone 录屏碎成 234 个（Chrome 230 个），揭示阶段还因此超出线程构建的 2 GB 内存上限而中止。救回后 g 为 0 个片段，iPhone 录屏为 1 个；八段 SDR 真实录屏的画布数、片段数和低置信放置数都与改动前相同。量到的 8 步真实步长：次优残差 / 残差 2.07–3.73，截尾 / 次优 0.06–0.25；其余候选都落在 1.1 倍以内和 0.66 以上。侧栏没有被单独学成固定区域，这本身仍是区域学习的待办。
- **只因落在两个像素之间而被残差平均值拒绝的一步，也按救回处理**（`rust/long-screen/src/kernels/track/odometry.rs::measured_between_pixels`，`rust/long-screen/src/kernels/motion.rs::sampling_insensitive_error`）：录屏被按非整数倍缩放过（0-1 是 0 缩到 0.804 倍再压缩的副本）之后，页面每一步都移动非整数个像素，而原生精修的采样点都取在最强的边缘上，正确整数位移上的残差于是随相位涨上去：0-1 的 393 步里有 303 步残差在 14.2–47.7，其中 185 步（27.1–47.7，次优 45–62）按上一条的比例也救不回来；原尺寸的 0 里平均值能跟上 392 步。0-1 因此几乎全靠重新捕获锚点跟踪，残差在 9–12 之间，门槛是 12，哪一帧碎成新片段取决于解码出来的细微差别：Chrome 和 WebKit 的结果、5b7fa66 前后的结果都会互换。现在被平均值和比例都拒绝的一步，再用 Birchfield–Tomasi 的取样不敏感差异量一次同一个位移：每个值和另一帧对应位置半像素范围内（到上下左右四个邻居的中点）的取值区间比较，两个方向取较小的一个。它低于 14、而相距两个像素以外的位移都不低于 14 且高出 1.5 倍以上，这一步就作为救回交给调用方，同样只在本来要开新片段时才用。位移仍取平均值找到的那个（不敏感差异在一个像素以内是平的），残差和置信度仍按原残差算。0-1 上那 185 步的不敏感差异是 0–12.5（中位数 0.17），相距两个像素以外 22.8–34.7；重复的行（三像素一个周期）因为次优同样低而不救。只在平均值拒绝时才算这一项，所以今天能跟上的帧一律照旧：17 段真实录屏里只有 0-1 和 test_5 的输出变了。
- **重新捕获锚点给出的一步与救回的一步相差 16 px 或以上时，不用重新捕获**（`rust/long-screen/src/kernels/track/verdicts.rs::reacquisition_contradicts_rescue`，`rust/long-screen/src/engine/solve/region.rs::reacquire_step`）：这一帧仍按丢失处理，先关键帧重定位，失败再用救回。两者量的是同一帧，都对时只差一两个像素，这时仍用重新捕获，因为它不带累积漂移；相差 16 px 以上（与闭环判不一致的距离相同）时，实测每一次都是救回对。实测失败：owner_1.49.38（在 Mac 上浏览维基百科长条目的录屏）里两者同时给出的 176 帧，130 帧相差不超过 3 px；其余 46 帧中，第 230 帧的重新捕获落在周期性正文的一个别名上（歧义，置信度 0.04，差 1790 px），此后第一趟、接回的片段、第二趟和第三趟开头整体偏 1790 px，长图中部出现第二个页面标题；第四趟快速往回甩动时，44 帧的重新捕获在一块不随页面上下滚动的面板上以零位移对上锚点（维基百科的「外观」面板，水平平移时会跟着动，所以被区域学习算进了滚动层），不歧义，置信度 0.38–0.53 还高于救回的 0.25–0.44，位姿一次次被拉回，累计偏到 11 629 px，留下整块空洞和第二个页面顶部；还有 1 帧差 442 px。所以置信度门槛和比较置信度都分不开这一类，只有「两个测量互相矛盾」能分开。改后这段录屏被拒的闭环从 47 次降到 0，第 230 帧落在 20633，第二趟顶端在 −192，第四趟回到页面顶端时约为 0，改按救回走的各步与独立配准一致；其余 19 段真实录屏的输出逐字节不变，其中包括前一条救回规则当初针对的 g 的侧栏、iPhone 的半透明标签栏和 0-1 的非整数缩放。代价：第四趟里前一帧严重运动模糊、里程计没给出救回的两帧（1462、1463）以前靠吸到面板上被放进长图，现在开新片段，1462 这一帧单独输出为一个片段。这条规则也管不到没有救回的帧：甩动中模糊的第 1510 帧没有救回，重新捕获照旧在面板上以零位移对上锚点（步长 0，真实 −652，改前也是这样）；从 1463 开始的片段按 1510 之后的帧接回，第 1463–1509 帧于是比较早几趟放的同一内容偏约 652 px。

- **低对比相位救援与输出范围分开，且只在救援实际被使用后启用内部配准区**（`rust/long-screen/src/kernels/track/phase.rs`、`rust/long-screen/src/engine/solve/region.rs`）。Apple Maps 原片的正确平移得到取样不敏感残差约 3、远处次优约 9–11，原有次优 ≥14 的绝对门槛把它拒绝；固定比例尺和边缘控件又干扰原生取样与 keyframe。新增救援要求低绝对误差、相对和绝对分离、独立 analysis audit 及足够分散的 unique feature 支持；仍先尝试 anchor／relocalization。只有新救援实际接住本来要分片的帧，才按 feature envelope 建立内部配准区。若提前启用，未被使用的 rescue 也会改变后续轨迹，实测仍碎成两片。odometry 与 keyframe patches 必须使用一致支持区，但原 region、`roi` 原点及输出 footprint 保持不变；改变 `roi` 会破坏 region-local patch 坐标。内区缺纹理时退回完整区；大步长仅在边缘有重叠时，再量完整区的非零位移作为后备 rescue，不能让固定 UI 的零位移取代 lost，也不能抢在 anchor 前使用。没有这个回退，640×480 真值夹具的 420 px 跳转会漏掉正确位置。完整地图从 140 个非空片段降为 1 个，合法观察覆盖无透明缺漏，但标签时刻混合与边缘 UI 残留仍未解决。

### 合成与瞬态像素

- **`TemporalRegion` 的 `complete` 意思是「这次观察重写了该块以前覆盖过的每一个像素」**，不是「该块有 256 个覆盖像素」。只有部分覆盖历史的块，以部分覆盖达成 `complete` 是合法的（一次放置的编排——瓦片顺序、冲突分量、`resolveTemporal` 的决策与 `overwritePatch`、诊断——在 `rust/long-screen/src/engine/compositor.rs`；`src/core/compositor.ts` 只是宿主，负责读写 `temporal/` 行与格式化诊断文字；连通分量与决策（`TemporalIndex::decide`/`mask_complete`/`commit`）在 `rust/long-screen/src/kernels/temporal.rs`，单瓦片的逐像素合成在 `rust/long-screen/src/kernels/compositor.rs::composite_tile`）。
- **`Compositor.resolveTemporal` 的 `maskComplete` 检查是整个连通冲突分量上的全有全无，不是逐像素的。** 带着指针/悬浮按钮的观察不是一个好的「完整时刻」，即使它是该区域的第一次完整视图。这是单独设计的不变式，不要随手放宽；它也**不是**覆盖物污染残留的原因（已逐像素查证排除，见 issue #2）。
- **任何相邻帧都无法比较的像素默认为一致，不是不一致**（编排在 `rust/long-screen/src/engine/render.rs`，逐像素判定在 `rust/long-screen/src/kernels/consistency.rs::consistency_mask`）。只出现在一帧里的内容（`glimpse` 场景）仍然必须画出来；把「没有证据」当成「拒绝」会让每个首尾帧和每次短暂回访变成窟窿。
- **越过页面边缘露出的底色在合成时留空；边从运动里读，留空多少由像素决定**（`rust/long-screen/src/kernels/overscroll.rs`，`rust/long-screen/src/engine/overscroll.rs`，§七「弹性越界」）。实测失败：合成器把弹性越界露出的窗口底色按世界坐标写进画布，揭示又从越界帧整块拷贝，画布范围是所有放置矩形的并集，于是长图多出只覆盖部分行列的边条，边上呈阶梯状缺口——owner_2.01.28 的 3834×6839 里有 402,441 个透明像素，owner_1.53.20 的 5318×8630 里 1,130,615 个，test_4 的 9186×7011 里 2,515,477 个，test_1 的 4589×6686 里 506,436 个；test_5 四周是看图应用的黑边。改后前三张是 3771×6736、5220×8233、8928×6222，没有一个透明像素（test_4 是 Chrome 打开的一张图，停在顶端的第 20 帧和停在底端的第 960 帧里画都顶到区域边缘，画上下那片深色只在回弹里露出过）；test_1 是 4539×6395，剩下的 116,645 个透明像素在右边那条浏览器滚动条轨道旁（轨道钉在屏幕上、被区域学习留在运动层里，不是底色，那一条不会被留空）；test_5 是 4421×6493，上、左两条黑边没了，下边只剩十几行；test_8 顶上多出的 112 行聊天底色没了（7737 → 7625）。几条构造各有原因：边取停留最多的值，不取最外侧的回弹，因为按住越过边缘时也会停（test_5 第 124–140 帧停在 −117）；没停稳就被拖走的回弹（test_3 停在 −43 两帧就往下滚）只能从页面停留过的位置找边；越界上限是区域的四分之一，因为 `fixture` 场景那种匀速的平移来回（320 px 的视口里往外 100 px 再匀速回来）在 2/5 的上限下被当成了回弹，而它右边几列卡片间的空白在片源噪声内是同一个颜色，像素检查拦不住；像素检查从外沿往里数、遇到页面内容就停，所以运动读出的边靠里时也不会剪掉内容（test_5 右边的边读成 1468，真正的边约在 1483，越过它的 464 帧一行都没留空）。钉在屏幕上的东西只在连续不超过 32 行、后面还接着底色时才跟着留空：不加限制时 test_3 页面顶端上方那一摞「登入」按钮没了，但 test_2 运动层里那块侧栏推广在页面底端的干净副本也被撕碎了——那块侧栏本来就该是固定区域（区域学习的待办），按钮也一样，所以 test_3 这次没有改变。代价：在录到范围的最外侧，普通往回滚和弹回在运动上一模一样，只靠「那一条里没有页面内容」区分，所以一大片纯色的页面区域（与底色同色的留白）如果只在一次往回滚里露出过，仍可能被当成底色剪掉；运动层里钉着的输入框（f）在页面底端改由别的帧来画，发送按钮上方多了一小块缺口。`glimpse`、`vertical`、`horizontal`、`fling`、`fixture` 和其余场景的指纹逐行不变。
- **瞬态像素可以被一致的观察覆盖修复，即使所在块是 `frozen` 的。** `frozen` 防的是重新挑选某个时刻，不是修复屏幕覆盖物的烧录；像普通替换那样用 `!frozen` 挡住修复路径会让烧录永久化（§七）。
- **`identical === count` 短路必须保留 `&& !provisionalInBlock` 例外**；反过来，降级规则刻意不作用于被逐位完整复现的块——那是佐证而非反证（§七）。
- **降级判据必须是逐位相同，不是容差。** ≤10 的容差会连「确实不同但接近」一起抓进来，而那正是块级冲突逻辑负责的事（§七，`tests/unit/compositor.test.ts` 两侧都有断言）。
- **`MediaInfo.noise` 只是片源的属性。** 不要把它变成设置项、按场景的覆写或相似度阈值。世界一致性掩码的每一次比较、以及 `Ring.tau`，都从它导出（§七）。
- **一致性投票的几条构造缺一不可**：`Ring.radius = f` 随分析因子缩放；只在内点格比较（`RegionSlot.interior`）；参照帧「最近两个 + 最远一个 + 分段内挑比较次数最少者」；结算是比例阈值而非字面全票；结论是三态而非一份位图；`Ring::box_gray` 在 f>1 时区域掩码 + 边缘复制、在 f=1 时完全关闭。每一条都对应一次实测的假阳性或漏报，推导见 §七。
- **渲染会话的帧环装新帧时，不复用正在合成的这一帧和它前后帧所在的槽**（`rust/long-screen/src/engine/render.rs::FrameRing::fill`）。只按「最早装入的槽先复用」时，连续两帧什么都不画（重复帧）之后，下一帧 t 先装自己、再装 t−1，于是第 t+1 帧装 t+2 时正好挤掉 t 的槽，掩码把 t+2 的像素当成 t 来比较。合成场景 `traversal`、`fling`、`vfr`、`fixture` 共五次，公开录屏 test_2 中 571 次；修正后 test_2 末尾约两万两千个被两帧拼坏的文字像素恢复清楚，同一张画布上另有一个 16×16 块改留了头像图片加载前的白色占位——那是这块第一次完整出现时的样子，稳定策略本来就保留它，原先是错误的掩码碰巧把那几帧判成了不一致（`test-results/frame-ring-fix/`）。
- **`consistencyMask()` 的「唯一邻居例外」只在该像素恰好有一个可比较邻居时适用。** 放宽到两个邻居实测让 `chrome-everything` 从 4.2k 涨到 27k（§七）。
- **屏幕固定区域每个像素取最后一次一致的观察，不建时间冲突记录**（判定在 `rust/long-screen/src/kernels/consistency.rs::fixed_mask`，写入看 `Observation.latest`，`rust/long-screen/src/engine/compositor.rs` 对 `Placement.fixed` 不建记录）。固定区域的一致是"至少与一个相邻帧相同"，不是移动区域的"与每个相邻帧都相同"：淡入后的第一帧只与下一帧相同，而下一帧被 `fixed_update` 跳过，换成移动区域的规则，稳定状态永远写不进去。改回按记录挑时刻，指针轨迹、半淡入的菜单栏、高度不是 16 倍数的栏会重新烧进固定画布；给记录加掩码也不行，沿指针轨迹合并的记录要求整条同时一致（§七，`menu-bar` 场景）。`frozen` 只出现在移动画布上。状态一直在变的固定区域（多于两成、且多于 10 帧有块稳定到新状态）例外：渲染结束时改回原样的第一帧（`RenderSession::begin_finish`，两个宿主在最后一帧之后像处理一帧那样走完它），因为 test_8 的半透明顶栏下面一直在滚聊天，取最后的状态会留下录制结束时的蓝色气泡；按块计数分不开它和真实的菜单栏（§七）。

### 揭示

- **统计要对共识再学一遍。** 第一遍的参照是已渲染画布，它自己带着鬼影；只用第一遍时 f 的页脚认不出来（§七「揭示」）。
- **一段相同位姿只投一票，用这一段的最后一帧；段末覆盖物活动区里仍在变化的格降为边缘。** 每帧都投票会让一段静止期反复给同一个（可能正在淡出的）状态加票；去掉段末降级，c 页面末尾正在淡出的滚动条滑块会被当成干净内容。降级只限覆盖物活动区：放到整层，0-1 里还在加载的页面内容会被误降。
- **整块写入要求严格一致（零个亮度离群格）。** 只要求宽松一致（允许两格离群）时，带着鼠标尖的视图会被整块写入，`dynamic` 场景留下 57 个污染像素（棘轮是 0）。
- **只有一次干净视图撑起的共识不能让边缘视图替换合成器的块。** d 滚得很快，层右缘的块往往只被完整看到一次，而那一次正带着没被认出的滚动条滑块；共识就是这一次视图，边缘视图与它「一致」后无条件写入，d 的右缘因此多出一串滑块碎片。
- **页面颜色的纯色竖条不沿整列按颜色认格**（`rust/long-screen/src/kernels/reveal/locate.rs::page_coloured`）。页面旁一条固定不动的白条（其实是页面边距：已渲染画布在那里还带着烧进去的滚动指示条，观察到的却是白色）会被学成颜色就是页面白色的不透明纯色物体；它又细又长，活动带沿整列伸到层边缘，按颜色认格就把这一列里每个干净的页面格都标成不透明，真正的 iOS 滚动指示条不是这个颜色，只因挨着它们被标成边缘，等级反而更好，于是在逐像素兜底里靠少数帧胜出：test_7 那一列 1,119 块里约 1,050 块原本合成器写的是页面，揭示阶段反而换成了滚动条。现在竖条每一帧先看活动带左右紧邻的两列格子，有一半以上是这个颜色就不按颜色认格；真滑块不管多长都和旁边的页面不同色，照旧认得出。只把活动带缩回物体自身的框不行：test_6 真正的灰色滑块要靠整条活动带认出来，缩回去它的滚动条从 2,142 行涨到 3,139 行。横跨整层的页面颜色横条仍按颜色认格：那是真正盖住页面的工具栏或输入栏底色，放开后 a（Dock 上方的深色横条）和 e（层底部的深色横条）都把别的时刻的块拷了进来。实测（打印图 x 1298–1312 上滚动条的行数）：test_7 17,237 → 611，test_8 7,455 → 296，test_6 2,142 → 32；test_1 和 e 右缘烧进去的滚动条也少了，g 的鼠标指针轨迹、c 的一个指针没了；a、d、f 和其余录屏的输出不变。
- **多色轨道里的移动部件必须以实际形状和可反驳的运动解释定位，不能增加全轨道颜色键。** test_1 的滑块与轨道背景被平均成一个长模板，真正的灰色滑块反而被当成 clean；按全部颜色键控曾在 test_6 引入新碎块。`reveal::controls` 在已学到的不透明长轨道中追踪紧凑连通部件，至少三次唯一匹配、运动不符合页面，而且前一次部件按页面运动应在的位置确实可观察却不匹配，才回填该实例实际出现的遮罩。正文底线即使与另一条形状相似，只要页面运动解释仍成立就不能当控件；区域外或遮蔽处不能充当“不匹配”。复用定位的 Cells，历史遮罩与元数据一同计入上限，满额后连空影格索引也不能继续增长。新等级只影响选源，不擦掉输出范围，也不平均像素。
- **动态分量的时刻避开不变块里有离群格的帧，不论离群格是几个还是整块。** 原先只认「零星几格」（一块里 1–24 格）算带着瞬态，好躲开扫过控件边缘的鼠标指针；整块都不一样的帧照样能当时刻。owner_1.53.20 里粘性目录形成的动态分量取了第 510 帧，那一帧左栏正好有 Chrome 的链接状态气泡，盖住了分量里几个整块：8 次干净视图里 7 次是页面、1 次是气泡，合成器原本写的是页面，揭示阶段反而把气泡拷了进来。这只是排序上的偏好，不是排除：这条上下文偏好保留在新的时刻排序中，并高于预测的洁净等级。较弱的初期共识也不能否决后来更干净的边界观察，否则 test_3 的缩图底部会退回带浮层残字的旧像素。动态块另用完整观察之间的一致性佐证时刻；静止段末的实际前一帧能确认刚加载完成的内容，不需要重复位姿增加票数。此规则的最初对照见上文。
- **离群格用亮度判定，不用色度。** 色度 4:2:0 重建在锐边上随位姿奇偶变相位，用逐通道判定曾把 f 的蓝色图标和 0 的缩略图拆成两个时刻。
- **兜底块只在更干净的观察与合成器像素矛盾时改写。** 无条件取多数会把 a 里只出现在少数帧中的细线抹掉。
- **覆盖物只在投票帧里定位，边缘膨胀只在不透明格附近做。** 两者都不改变结果（四段真实录屏的原生 harness 输出逐字节相同），只省掉整层遍历。格均值仍然每个投票帧整层并行算一遍：改成按需逐格计算在原生单线程下更快，在 Wasm 线程构建里却更慢（b 的核对核心时间 1.9 s 变成 3.4 s），因为整层分给 8 个 helper 并行，而按需计算只在一个线程上做。`Reveal::wanted` 与 `Reveal::frame` 必须用同一条规则，否则会读到没有转换过的帧。

- **先找变动核心，再分配静态边界，边界不能合并独立物件。** Apple Maps 中先膨胀再连通，把地名和道路串成 1,499 块的群组，几乎不可能同帧完整观察；只把九成提交改成完整提交仍会退回片段混写并切掉 Columbia。核心先分组、边界唯一归属后，这个新缺字消失。对完整时刻的当前签名，只在其 bbox 可能完整出现在当前帧时分配，暂存预算按视窗估算；不能按整个巨大画布反复分配临时签名。
- **静态桥也可能属于同一个动态物件；协调时刻必须有实际的同帧完整观察。** `document-slider` 的 140×12 长条在文件中左右移动，中间始终相同，两个变动核心各自完整却选了不同帧，输出被拉长到 190 px（2,280 个像素；每一输入帧只有 1,680 个）。`blocks::moments` 只在当前帧完整观察了相邻群组、每个成员块至少达到已有群组时刻的 veil 等级、静态上下文无亮度离群时（与时刻排序相同：比共识等级更干净的观察不受较弱参照否决），才联集它们原本拥有的区块并用这个完整时刻一起更新。视窗外、遮罩孔洞、opaque／fringe 或矛盾上下文都不能当证据；边界相接本身仍不够。test_3 的一张缩图原本因 veil 等级上下文残影拒绝合并，被拆成第 840／842 帧三块；对齐后整张取自第 840 帧。合并不新增所有权，不把未观察间隙算进去，稀疏 bbox 不能造成无上限的稠密遮罩配置。后续按完整群组选择来源，不能再分别更新两端。合并也不能重置已建立的时间证据：当前观察不得低于任一成员已选时刻的等级；已有选择的成员须有相同的当前证据等级，再带入按世界块排序的相容签名。否则第一次共同可见时的单帧脉冲会取代旧稳定内容，或合并后的下一帧脉冲会因历史被清空而胜出。见 `tests/unit/component-moments.test.ts`。
- **局部相位解释不能拆散本来可观察的物件。** 小位移既可能是配准相位，也可能是真正的物件运动。全域抹掉相位解释的变化计数，曾在 test_6 新增标题下方白碎片，并让地图边缘图示选入原视频的半幅绘图。保留原始变化计数，另记相位支持；只有原始变动核心的最小可能跨度仍超过实际视窗上界时，才启用相位分组。静态边界不是物件范围，两端各保留 `BLOCK-1` 像素的量化不确定度；未知视窗不拆。可容纳于一帧的群组继续整组协调，即使路径没有看全静态边界。地图过大道路群组可拆，控件与边缘图示则保留一致来源；没有按素材或输出 hash 分支。
- **相位需要结构证据。** 只在原比较已判变化时检查一个签名格内的刚性位移；重叠区必须包含被平移解释的结构，不能裁掉四边新标记后用平坦匹配证明相位。两类生成物件反例分别在全域相位版留下 1,536／1,024 个错像素，范围约束后恢复。
- **不能用「更靠中央」替代内容佐证。** 无条件位置优先使 `chrome-everything` 取带游标的第 48 帧，比原算法多 85 个可修复污染像素；先检查动态内容在完整观察间是否得到佐证，再比较可见性，才同时保住地图标签并避免游标回归。影格第一次出现的新状态不等于稳定状态，静止段最后两帧则可以直接佐证新状态；持续动画没有可佐证时刻时仍保留可用的最新完整观察。
- **低斜率本身不能证明覆盖，参照讯号也必须高于噪声。** 同对比度的平移相位会降低回归斜率，原模型因此把干净地图误当成 veil；只有几个灰阶级变化的白边参照，也曾让干净白边误判成不透明物体，再让较模糊的顶缘来源胜出。回归先要求参照对比度高于既有的一致性噪声底，再要求实际对比度下降或重复可见差异所支持的显著有向亮度偏移。不能只要求整段方差降低：半透明控件间歇出现时，开／关混合反而会增加总方差，曾让 test_5 新增捲轴残影。平均偏移的不确定度按实际视图数估计，不把池化邻格当独立样本。相位噪声、纯色页边／微小参照噪声是负例，真实衰减、间歇 veil 与移动替换是正例。
- **有结构的模板必须用训练时稳定的量匹配。** 模板稳定性由亮度确定，却以 RGB 拒绝色度变化，会漏掉半透明控件。有结构模板核对亮度值与形状，无结构纯色模板仍核对 RGB；不能靠放弃形状或关掉覆盖物检测通过。
- **低等级共识的平坦区升级需要两个实际观察及无结构边界。** 任意整块升级会在真实地图上新增道路断点；只看一块是否平坦也可能擦掉刚移到块外的细线。要求整个 3×3 块邻域都已观察且平坦、两个干净观察一致，才能取其中一帧的原生像素。该分支不平均颜色，不裁输出范围；抽除它会让已确认的淡色控件残留重新出现。

- **静态区块不能仅因细边小于绝对离群门槛就永久锁定，也不能永远服从旧参照。** test_6 的地址膠囊细边单格差约 46，小于原先 48，第一张错误视图被当作 `Coherent`，后面的干净视图不再检查。完整世界格邻域的局部对比度与解码噪声共同限制新结构，同时保留真实锐边、跨块边界的相位余量。弱新内容若持续出现，可由两张互相足够接近的干净观察佐证，避免真实新文字卡在早期空白；静止段的实际前一帧优先于更旧的见证，不能让旧相似状态替末帧脉冲背书。见证的储存／清除在串行套用阶段完成，平行决策不配置记忆体；静态见证与动态历史的区块所有权互斥，预算必须涵盖指针与签名。
- **空间上的相位相容不等于可以永久锁定。** test_6 的格子背景边缘有 24 个像素被 Safari 地址胶囊覆盖；它们来自第 115 帧，沿真实边缘的局部对比度足以解释其弱差异，于是过早进入 `Coherent`，以后干净的观察不再检查。`Act.strict` 保留空间接受性和延后选源资格；`Act.settled` 则要求每格与参照的亮度差处于现有噪声底两倍以内，或由另一个实际观察更严格地佐证，才允许永久锁定。有效但孤立的相位视图仍能由 `Edge` 延后输出，不丢掉像素。不要为解决这个问题裁掉范围、提高噪声容差、固定某个来源帧，或把参考的宽松一致计数当成逐格时间佐证。

### 瓦片缓存

- **瓦片缓存的下限是一帧画到的全部瓦片，按这一帧放置的每个区域分别算再相加**（`rust/long-screen/src/engine/tiles.rs::TileCache::ensure_footprint`，由 `rust/long-screen/src/engine/render.rs::RenderSession::configure_tiles` 传入所有非忽略区域）。一帧会把滚动区、固定栏、分隔带、粘性栏各自画进自己的画布；下限只按一张帧大小的画布算时，c 的五个区域装不进 50 块的缓存，LRU 几乎每帧把每块都重新解码一遍（170 帧解码 7,733 次，Chrome 13.4 s），按区域相加后是 91 块，解码 383 次、7.3 s，瓦片逐字节相同。内存预算设置不能把缓存压到这个下限以下；区域没有铺满整帧时，这个下限可以比按整帧算的更小。

### 呈现画布

- **呈现画布（`rust/long-screen/src/engine/framing.rs` 的 `FramingSession`，逐瓦片绘制在 `rust/long-screen/src/kernels/framing.rs`，`src/core/framing.ts` 只是宿主）必须保持 O(周长瓦片 + 已观察源瓦片)。** 那个只做网格算术与查找、不碰像素的前置规划，正是为了让大面积装饰背景不会强制一次完整包围盒扫描；去掉它会把稀疏外框变成意外的稠密画布。规划超过瓦片上限时在碰任何瓦片之前跳过；只看周长就已超限时，连源画布的瓦片索引都不读。
- **外框用去掉瞬态的参照帧**（渲染结束时 `RenderSession::patch_reference` 把每个固定区域去掉瞬态的第一帧画到 `frame-reference` 上，两个宿主再存一次这一行；`FramingSession` 不变）。参照帧是第 0 帧，原样照搬时第 0 帧里停着的指针会出现在每一张带外框的成品里：test_2 外框 (3135,125)、owner_1.53.20 外框 (5020,170) 的指针就是第 0 帧里的指针（与第 0 帧的平均差只有 0.02 和 0.003）。外框不改用固定画布最后的样子，因为外框要和正文顶部对得上：c 左侧 990 px 的固定区域里有一段 GitHub 页头，页头滚走以后是空白，用最后的样子外框就和正文的页头错开；test_8 的外框顶栏也会变成蓝色气泡上的样子。所以只换掉第 0 帧里指针大小的瞬态，第 0 帧的布局（比如 test_2 全屏时隐藏的菜单栏）保持原样（§七）。

### 界面语言

- **共享的 `src/i18n/index.ts` 从不读取 `navigator` 或存储，默认 zh。** Deno 也有 `navigator.language`；共享模块一旦读取它，单测、场景指纹和导出文本就会随主机语言变化。只有页面端的 `src/i18n/page.ts` 检测语言，worker 在收到任何命令之前由页面发来的 `locale` 消息得知语言（`src/ui/rpc.ts`）。
- **zh 目录里的文案就是持久化文本。** 诊断的 `message`/`action` 按运行时的界面语言写入并持久化，场景指纹按 zh 计算；改动一条 zh 文案会改变指纹，这是需要解释的变化，不是噪声。
- **区域与画布名称是固定的 zh 词表，只在显示时翻译**（`src/i18n/names.ts`）。`rust/long-screen/src/kernels/regions/crops.rs` 按 `固定分隔界面` 这个名字查找分隔带，parity oracle 与已保存的项目也都存着这些名字；在创建时就按界面语言命名会同时破坏这三者。

### 测试

- **`src/synthetic/verify.ts` 只在覆盖物实际绘制过的像素上记录 overlay 颜色**（与 `RenderedFrame.beneath` 比较）。overlay 的 rect 是包围盒，有些覆盖物只画其中一部分（鼠标指针是 10×16 盒子里的一个箭头）；按整个 rect 记录会把页面坐标的动态内容算成屏幕覆盖物污染，并错误地在 `contaminatedOverlay` 与 `contaminatedDynamic` 之间划分。
- **各场景的棘轮只能往下调**（`maxMissing`/`maxInvented`/`maxMismatched`/`maxContaminated*`/`maxProvisional`）。调高一个来让运行通过是在掩盖回退。调高需要的是一个查清的机制，不是一次测量；`maxContaminatedOverlayRecoverable` 对任何没有查清理由的场景保持默认 0。

## 十一、代码地图

下面按目录列出每个模块归属，标注它属于哪一层：**TS 外壳**（细分为 UI / worker RPC / 浏览器 API / I/O / 编排）、**Rust 算法核心**，或**绑定**（TS↔Wasm 的双向封送层）。清单由 `find src rust/long-screen rust/wasm/src -type f | sort` 生成，不是凭记忆写的；出现分歧以树本身为准。

**一域三文件规则**：算法核心的每个领域都拆成三个同名文件——`rust/long-screen/src/kernels/<域>.rs`（纯算法，无 FFI）↔ `rust/wasm/src/<域>.rs`（该域的 `extern "C"` 导出，序列化/反序列化）↔ `src/core/wasm/<域>.ts`（TS 侧的对应封送模块）。例如 `raster`：`raster.rs` 算法、`rust/wasm/src/raster.rs` 导出、`wasm/raster.ts` 封送。两个域例外，都是因为体量被拆成多文件：`regions`（算法侧 `rust/long-screen/src/kernels/regions/{mod,atlas,bands,band_fn,cells,construct,crops,merge,tests}.rs`，binding 侧仍是单个 `rust/wasm/src/regions.rs` ↔ `src/core/wasm/regions.ts`）与 `track`（binding 侧也拆成 `rust/wasm/src/track.rs` + `rust/wasm/src/track_{odometry,reacquire,keyframes}.rs` ↔ `src/core/wasm/track.ts` + `wasm/track-{odometry,reacquire,keyframes}.ts`，算法侧仍是单个 `rust/long-screen/src/kernels/track.rs`）。`pool`/`geometry`/`region`（单数，`filter_features` 等，供 `regions`/`framing`/`voting` 共用）没有对应的 `rust/wasm/src/*.rs` 独立入口或被多个域共用，不算独立的"域"；`png`/`yuv` 现在各自都有完整的三文件（`png.rs`/`rust/wasm/src/png.rs`/`wasm/png.ts`，`yuv.rs`/`rust/wasm/src/yuv.rs`/`wasm/yuv.ts`），不再是例外。引擎库（§十三）的各遍同样一域三文件，只是算法侧在 `rust/long-screen/src/engine/<域>.rs`：`scan`（`rust/long-screen/src/engine/scan.rs` ↔ `rust/wasm/src/scan.rs` ↔ `src/core/wasm/scan.ts`）、`diagnostic`；`framing` 与 `pyramid` 的 binding 两侧各只有一个文件，背后同时是 `rust/long-screen/src/kernels/<域>.rs` 的逐瓦片内核和 `rust/long-screen/src/engine/<域>.rs` 的会话；`layers` 的 binding 两侧仍是原来的 `rust/wasm/src/layers.rs` ↔ `src/core/wasm/layers.ts`，背后同时是 `rust/long-screen/src/kernels/layers.rs` 的累加器和 `rust/long-screen/src/engine/layers.rs` 的 `RegionLearner`。

### src/core（绑定层 + 少量仍待迁的算法转发）

- `wasm.ts` — 桶文件，把 `src/core/wasm/*` 的每个导出重新导出给三十多个调用方（现测 31 个，数字随新文件漂移，不必追求精确；用 `grep -rl "from '.*core/wasm\.ts'"` 之类的命令重新数），保留 `import { core } from './wasm.ts'` 这条旧路径。绑定层。
- `wasm/core.ts` — `Core`：加载/持有 Wasm 实例（含可选的线程池）、`core().x(...)` 的统一入口，把每个内核调用委派给对应域模块。绑定层。
- `wasm/exports.ts` — `rust/wasm/src/*.rs` 导出的 `extern "C"` 签名类型、内存布局常量、状态码约定。绑定层。
- `wasm/loader.ts` — `planCore()`：按 SIMD128/threads/crossOriginIsolated 能力选择 scalar/simd/threads 三种构建之一并加载为 `active` 单例。每个构建的地址由 `coreURL()` 各写一个字面量 `new URL('./core….wasm', import.meta.url)`，不拼文件名，打包器（npm 包的使用者）才认得出来。绑定层，兼 TS 外壳（浏览器能力探测）。
- `wasm/marshal.ts` — 每个域模块写入核心内存的公共封送原语（`writeRect` 等）。绑定层。
- `wasm/memory.ts` — 核心内存所有权：bump arena 的规划、`Resident`/`ResidentFrame`/`ResidentGray`/`FrameRing` 等跨调用常驻句柄。绑定层。
- `wasm/raster.ts` — 像素格式转换与逐像素光栅内核封送（镜像 `rust/wasm/src/raster.rs`）。绑定层。
- `wasm/features.ts` — 角点/描述子提取、匹配、视觉词封送（镜像 `rust/wasm/src/features.rs`）。绑定层。
- `wasm/motion.ts` — 平移/缩放假设、audit、精修、运动场封送（镜像 `rust/wasm/src/motion.rs`）。绑定层。
- `wasm/chrome.ts` — 固定边界与吸附遮挡带检测封送（镜像 `rust/wasm/src/chrome.rs`）。绑定层。
- `wasm/consistency.ts` — 世界一致性掩码封送（镜像 `rust/wasm/src/consistency.rs`）。绑定层。
- `wasm/compositor.ts` — 引擎合成器 `CompositorHandle`（一次放置的 `begin`/`step`、时间记录的载入与 flush、诊断解码）的封送（镜像 `rust/wasm/src/compositor.rs`）。绑定层。
- `wasm/tiles.ts` — 引擎瓦片缓存 `TileCacheHandle`（驻留、LRU 换出、预算、脏标记、计数，瓦片平面所在的核心内存指针）封送（镜像 `rust/wasm/src/tiles.rs`）。绑定层。
- `wasm/temporal.ts` — 时间记录的线格式（`TemporalRow` 头 + 块），引擎合成器的封送读写它（镜像 `rust/wasm/src/temporal.rs`，那边另有一个只给 ABI 测试用的 `ls_overwrite_tile`）。绑定层。
- `wasm/framing.ts` — 引擎呈现画布会话 `FramingSessionHandle`（参照帧、源瓦片索引、`step` 的结果解码，缓存在中途换出的输出瓦片交回时拷出平面）的封送，另有只给测试用的 `frameLayout`/`frameCoordinate`（镜像 `rust/wasm/src/framing.rs`）。绑定层。
- `wasm/pyramid.ts` — 引擎金字塔会话 `PyramidSessionHandle` 的封送，另有 parity 测试单独核对的父瓦片装配 `assemblePyramidParent`（镜像 `rust/wasm/src/pyramid.rs`）。绑定层。
- `wasm/png.ts` — 单 PNG 导出路径的扫描行 (un)filter 封送（镜像 `rust/wasm/src/png.rs`）。绑定层。
- `wasm/pose-graph.ts` — 引擎位置图状态对象的封送（镜像 `rust/wasm/src/pose_graph.rs`）：节点和要写的行解码成与原来字段顺序相同的 JS 对象（`next` 只在设置后出现，排最后）。绑定层。
- `wasm/keyframes.ts` — 引擎关键帧索引状态对象的封送（镜像 `rust/wasm/src/keyframes.rs`）。绑定层。
- `wasm/render.ts` — 引擎渲染会话的封送（镜像 `rust/wasm/src/render.rs`）：plan、投票记录、画布元数据进，观察台账行与诊断出；台账行按原来的字段顺序逐个构造（`skip`/`occlusions`/`skipped`/`reusedExactObservation` 只在原来有时出现）。绑定层。
- `wasm/bytes.ts` — 引擎记录用的小端字节读写器（字符串是 u32 长度加 UTF-8），镜像 `rust/wasm/src/bytes.rs`。绑定层。
- `wasm/layers.ts` — 图层学习器 handle 封送：逐帧证据累加、累加器读回、`finish()` 建区域（镜像 `rust/wasm/src/layers.rs`，背后是 `rust/long-screen/src/engine/layers.rs::RegionLearner`）；扫描趟用的是扫描会话自己的学习器，这个 handle 留给图层学习的单测与 parity 测试。绑定层。
- `wasm/scan.ts` — 扫描会话 handle 封送：把解码帧拷进会话自己的帧缓冲、`isDuplicate`、`push` 一帧并把返回记录解码成 `ScanRecord`/`CompactFeatures`/结构化诊断（运动场按产生它的分支还原键序）、`finish` 读回区域；另有 `estimateMotion` 的单次调用（镜像 `rust/wasm/src/scan.rs`）。绑定层。
- `wasm/diagnostic.ts` — 引擎结构化诊断（code、severity、frame/time、数值参数，以及可选的画布、置信度、矩形和原样存进诊断行的 `detail`，不带文字）的解码（镜像 `rust/wasm/src/diagnostic.rs`）。绑定层。
- `wasm/solve.ts` — 引擎求解会话的封送（镜像 `rust/wasm/src/solve.rs`）：区域描述、帧槽视图、存储的紧凑特征、关键帧行的编码，以及放置、投票记录、要写的行（画布、接回、关键帧、位置图）和诊断的解码，解码出的对象与以前存的逐字段同序。绑定层。
- `wasm/regions.ts` — 一次性区域构建与原生分辨率像素打标封送，以及扫描会话/学习器交回的区域集合的解码（手放区域保留设置里的原对象，只补上引擎决定的 id、排除区与未指定区域）（镜像 `rust/wasm/src/regions.rs`）。绑定层。
- `wasm/track.ts` — 逐区域逐帧跟踪判定与关键帧候选评分封送的共用小工具（`b`/`b2`/`writePatches`/`resolveNative`），`export *` 重新导出下面三个拆分模块，供 `wasm/core.ts` 的 `import * as track from './track.ts'` 免改（镜像 `rust/wasm/src/track.rs`）。绑定层。
- `wasm/track-odometry.ts` — 逐区域逐帧里程计融合调用（`odometry`），从 `wasm/track.ts` 拆出（镜像 `rust/wasm/src/track_odometry.rs`）。绑定层。
- `wasm/track-reacquire.ts` — 重定位与漂移改正融合调用（`reacquire`/`driftCorrection`），从 `wasm/track.ts` 拆出（镜像 `rust/wasm/src/track_reacquire.rs`）。绑定层。
- `wasm/track-keyframes.ts` — 关键帧候选评分融合调用（`evaluateCandidates`），从 `wasm/track.ts` 拆出（镜像 `rust/wasm/src/track_keyframes.rs`）。绑定层。
- `wasm/voting.ts` — 位移展开一致性投票环 handle 封送（镜像 `rust/wasm/src/voting.rs`）。绑定层。
- `wasm/reveal.ts` — 引擎揭示会话（`long_screen::engine::reveal::RevealSession`）的封送：层与画布登记、观察行、内存检查的回答、会话自己的帧缓冲指针、逐帧推进与每一步的结果（要的瓦片、`wanted`、来源行、`REVEAL_SKIPPED`、汇总）（镜像 `rust/wasm/src/reveal.rs`）。绑定层。
- `wasm/yuv.ts` — 解码帧到 RGBA 的平面/半平面转换封送（`frameToRGBA`，供 Safari 等不支持 `copyTo` 直转 RGB 的浏览器使用；镜像 `rust/wasm/src/yuv.rs`）。绑定层。Deno 下会被 `core.ts` 桶文件间接引入而出现在覆盖率报告里，但函数体从不在 Deno 下执行，`scripts/coverage.ts` 给它单独的 0 下限而不是 BROWSER_ONLY。
- `helper.ts` — 线程构建（`core.threads.wasm`）的 pool helper worker 入口，在共享内存上实例化并常驻。TS 外壳：浏览器 API（Worker）。
- `id.ts` — `createId`：优先 `randomUUID`，非安全上下文回退 `getRandomValues`。TS 外壳：浏览器 API。
- `math.ts` — `clamp`/`median`/`pad`/`intersect`/`contains`/`norm`/`rng` 等与领域无关的纯数值/几何小工具，供 Rust 尚未接管的编排代码使用。TS 外壳（编排用的纯函数，未来若被算法路径复用可考虑下沉）。
- `raster.ts` — `analysisFactor`/`downscaleGray`/`RasterPose` 等转发到 `rust/long-screen/src/kernels/raster.rs` 的薄封装（重复帧判定 `equalRGBA` 已随扫描趟进了 `rust/long-screen/src/engine/scan.rs`）。绑定转发层。
- `motion.ts` — `estimateMotion`（一次调用，静止帧对跳过特征匹配的惰性判断已在 `rust/long-screen/src/engine/scan.rs::estimate_motion`）加两个仅供调用方沿用的类型别名（`NativeRefinement`/`Patch`）；`extractPatches`/`probeScale`/`refineNative`/`refinePatches` 这些一行转发在 d029e6b 被删，调用方现在直接用 `core().x(...)`。绑定转发层，兼少量编排。
- `layers.ts` — `LayerLearner`（学习器 handle 持有者；参照帧与手放区域分支都在 `rust/long-screen/src/engine/layers.rs`）、`RegionAtlas`（原生分辨率标签平面持有者）、`stationaryBoundary`/`stickyOcclusions` 的转发；`regionContains` 的 TS 副本已删（R6-B，过滤逻辑移进 `rust/long-screen/src/kernels/region.rs::filter_features`，见十二节 track 行），`informativeField` 已随扫描趟进了 `rust/long-screen/src/engine/scan.rs`。绑定转发层。
- `compositor.ts` — `Compositor`：引擎合成器（`rust/long-screen/src/engine/compositor.rs`）的宿主。`add()` 逐步驱动一次放置，按引擎的要求载入瓦片（`TileStore.load`）和 `temporal/<canvas>/` 行，再按目录格式化它报出的诊断；`flush()` 写回改动的时间记录。TS 外壳：I/O。
- `framing.ts` — `buildFramedCanvas`：引擎呈现画布会话（`rust/long-screen/src/engine/framing.rs`）的宿主——读 `frame-reference` 行并解码 PNG、把源画布的 level 0 瓦片索引交给会话、按会话的要求载入瓦片（`TileStore.load`）并立即存下它填好的瓦片、每个输出瓦片之前的暂停/停止检查点，最后按原字段顺序写画布行；`PRESENTATION_TOO_SPARSE` 的英文原文仍在这里。TS 外壳：I/O。
- `keyframes.ts` — `Keyframe` 行类型、`RELOCALIZATION_BUDGET` 的原样英文文字，以及 `KeyframeIndex` 宿主。求解趟已不用这个宿主（关键帧检索与评分在引擎的求解会话里，见 `rust/long-screen/src/engine/solve/`），它和 `evaluateCandidates` 只留给 `tests/unit/keyframes.test.ts` 与 parity 测试。原先的说明：关键帧行照旧写进 KV 的 `keyframe/`；视觉词倒排表、按词投票取前 12 个候选、每层一次的检索预算告警和“离当前帧太近不算回访”的判断都在引擎（`rust/long-screen/src/engine/keyframes.rs`），这里只读回候选行、发 `RELOCALIZATION_BUDGET`（原样的英文文字，不在文案目录里）并调用核心的候选评分；`evaluateCandidates` 仍是那次评分调用的封送（canonical 画布按 id 装箱成整数索引，再把选中的候选装回 `Relocalization`），详见十二节 track 行。TS 外壳：I/O + 绑定转发。
- `pose-graph.ts` — `PoseGraph` 宿主：`PoseGraph.adopt` 接过求解会话交出的位置图（不读存储），否则第一次调用时把 `node/`、`edge/` 读回交给引擎（`rust/long-screen/src/engine/pose_graph.rs`），引擎每次调用返回的 `put`/`putMany` 原样按序写回；`optimize()` 每步一趟松弛，步与步之间 await 检查点，停止时丢弃这次松弛、什么都不写。返回的节点是副本，解除固定走 `unpin()`。TS 外壳：I/O。
- `compute.ts` — `AnalysisComputer`：WGSL compute shader 做灰度+整数降采样，首帧 CPU/GPU 位精确校准与自动回退；只加速 `gray()`。`hostGray()` 供扫描趟用：走 WebGPU 时交出灰度图，走 CPU 时返回 `undefined`，由扫描会话在核心里自己降采样。TS 外壳：浏览器 API（WebGPU）。
- `wasm/*` 之外没有其它未列出的核心域模块。

### rust/long-screen/src/kernels（算法核心）

- `mod.rs` — `long-screen` crate 的 `kernels` 模块入口；这里没有 FFI，第三方依赖只有 `libm`（见下一段）和原生宿主才打开的 `rayon` feature，浏览器经 `rust/wasm` 的导出调用它。是实现层：公开是因为 `rust/wasm`、`rust/bench` 要用，API 在次版本之间可能变。Rust 算法核心（模块声明）。
- 超越函数（`exp`、`pow`、`log`、`hypot` 等）一律调 `libm` crate，不用 std 的 `f64::exp` 这类方法。wasm 构建里 std 的这些方法由 `compiler-builtins` 落到同一份 musl 代码上，原生构建却会调系统的数学库，个别输入上差最后一位（实测一次运动置信度 0.054445016798489 对 0.05444501679848899），一路传到位置与像素。直接调 `libm`，网页、命令行、Python 扩展和别人用这个 crate 写的程序算出的都是同一个数，也不用在可执行文件里替换 C 符号。`rust/long-screen/clippy.toml` 用 `disallowed-methods` 在整个 crate 里禁掉 std 的这些方法（算法核心、引擎、解码和驱动都在内），`deno task lint` 的 wasm clippy 和原生 clippy 会直接报错；解码里唯一的 `atan2`（AVFoundation 的旋转矩阵，结果取整到 90°，最后一位动不了它）带一个写明原因的局部 `#[allow]`；`sqrt`、`abs`、`floor`/`ceil`/`round`/`trunc`、`mul_add`、`min`/`max` 和 `%` 在 IEEE 754 下处处精确，照常用。`libm` 钉在工具链自带的那一份上（1.94.0 的 `compiler-builtins` 源码与 0.2.16 逐字相同），升级工具链时要重新核对，三种 wasm 构建的场景指纹会暴露差异（`test-results/libm-core/`）。
- `raster.rs` — 原生帧光栅内核：luma、盒式分析降采样、预览减半。Rust 算法核心。
- `features.rs` — 角点检测（3×3 结构张量最小特征值，整数前缀和）与二值描述子。Rust 算法核心。
- `motion.rs` — 平移/缩放假设生成、patch 误差、audit、整数精修。Rust 算法核心。
- `overscroll.rs` — 弹性越界（§七）：从一张画布的位姿轨迹求出页面四条边（`page_edges`），数一帧越界那一侧从外沿往里的底色行（`background_lines`）。Rust 算法核心。
- `chrome.rs` — 固定边界持续性外观边、吸附遮挡带检测。Rust 算法核心。
- `consistency.rs` — 单区域世界一致性掩码（±1 帧证据 + 投票环终审），以及固定区域的一致性（`fixed_mask`）。Rust 算法核心。
- `fixed_history.rs` — 固定区域每个像素的取值段，和由此得到的去掉瞬态的第一帧（§七）。Rust 算法核心。
- `compositor.rs` — 单瓦片像素归属合成：块级冲突/替换决策、coverage/provisional 记账、像素写入。Rust 算法核心。
- `temporal.rs` — 时间冲突连通分量、`overwrite_tile`、内存态 `TemporalIndex`/`resolveTemporal` 决策。Rust 算法核心。
- `framing.rs` — 呈现画布布局/坐标映射、背景扩展统计、逐瓦片两趟绘制（由 `rust/long-screen/src/engine/framing.rs` 调用）。Rust 算法核心。
- `pyramid.rs` — 四子瓦片（含空洞）减半装配为父瓦片；减半本身复用 `raster::halve_rgba`（由 `rust/long-screen/src/engine/pyramid.rs` 调用）。Rust 算法核心。
- `png.rs` — 单 PNG 导出路径的扫描行 (un)filter；瓦片编解码走 `rust/wasm/src/png.rs` 的 `png` crate 端到端路径，不经过这里。Rust 算法核心。
- `pose_graph.rs` — 单锚点简单环的解析解与 Gauss-Seidel 位置图松弛，纯数组/CSR 输入，不认识字符串 id。Rust 算法核心。
- `region.rs` — 泛型 `Region<M: AsRef<[u8]>>::contains`（矩形、排除区、可选原生裁剪、分析分辨率掩码查询，对掩码存储是拥有还是借用泛型化，供 `voting.rs`/`track.rs` 与 `regions::atlas` 共用同一份实现）与 `filter_features`（`ownFeaturesOf` 的区域成员过滤，R6-B 从 TS `regionContains` 移入）。Rust 算法核心。
- `regions/mod.rs` + `{atlas,bands,band_fn,cells,construct,crops,merge,tests}.rs` — 一次性区域构建流水线（并查集分格、条带检测、区域装配、原生精度裁剪、小块合并、最终过滤）与原生像素打标；逐阶段从冻结的 TS oracle（`tests/support/reference/layers.ts`）移植。Rust 算法核心。
- `layers.rs` — `LayerLearner` 逐帧累加证据（行/列分歧、split/evidence/activity），冻结为 `tests/support/reference/layers.ts` 的字节对照基准。Rust 算法核心。
- `track.rs` — 逐区域逐帧无状态跟踪判定（不确定度、重定位判定、attach/thin-overlap/loop-closure 判定、关键帧候选评分等），含 `odometry`/`reacquire`/`driftCorrection` 与关键帧候选评分的置信度 `exp()` 收尾，以及关键帧候选的排序/最强候选/对手歧义判定（`select_candidate`），见十二节。Rust 算法核心。
- `voting.rs` — 位移展开一致性投票环：ring buffer、box-gray、interior、partners、compare、finalize，有状态 handle。Rust 算法核心。
- `pool.rs` — 线程构建下把独立分块工作分发给共享内存 helper worker 的数据并行 `for`；原生构建打开 `rayon` feature 时分给调用所在的 rayon 线程池；其余构建内联顺序执行。Rust 算法核心（并行基础设施）。
- `geometry.rs` — 与 JS `Math.round`/`Math.floor` 精确对齐的取整/几何约定。Rust 算法核心（共享工具）。
- `yuv.rs` — 平面/半平面 YUV → RGBA（libyuv 参考算法），供不支持 `copyTo` 直转 RGB 的浏览器（Safari）使用。Rust 算法核心。
- `reveal/mod.rs` + `{stats,model,locate,blocks,run}.rs` — 揭示阶段（§七）：屏幕格统计（世界对齐取格）、覆盖物建模、逐帧定位与洁净等级、世界块共识/动态分量/写入决策、四遍的帧驱动与 `wanted` 规则；由引擎的 `RevealSession`（`rust/long-screen/src/engine/reveal.rs`）驱动。Rust 算法核心。

下面的路径相对 `rust/long-screen/`。

- `src/engine/pyramid.rs` — `PyramidSession`：一个画布的预览金字塔。层数用倍增计算；每层先要下一层的瓦片索引（`NeedIndex`，每行经 `queue` 排进父瓦片队列，宿主照旧写 `pyramid-todo/` 行），再按存储键的顺序逐个父瓦片要四个子瓦片（`NeedChildren`）、装配后交回（`Parent`，没有子瓦片时为空），每层结束报 `LevelDone`。不经瓦片缓存。Rust 引擎。
- `src/engine/presentation_host_tests.rs` — 原生宿主测试：只经公开 API，先用 `FramingSession` 在三块的小缓存上做出呈现画布，再用 `PyramidSession` 给它建金字塔。Rust 引擎测试。
- `src/engine/reveal.rs`（单测在 `src/engine/reveal_tests.rs`）— `RevealSession`：揭示阶段（§七）。先要内存（`NeedMemory`：所有画布、层与三帧的估计，宿主拒绝则以 `REVEAL_SKIPPED` 结束），再要观察行（`NeedObservations`：只留本阶段覆盖的画布与层上的决定，盲帧经 `admitted` 判定，位姿按页面的 `Math.round` 取整），逐行把合成器的瓦片喂进参照（每块之后一个 `Checkpoint`），然后四遍：每遍给出 `Decode`（含 `wanted`），宿主把要读的帧写进会话自己的帧缓冲（最多三块：投票帧、它前一帧、正在写的帧）后逐帧 `push_frame`、`end_pass`；写入遍之前先要回退状态的内存，再按块取合成器像素；投票后的整块拷贝按出现顺序逐瓦片写进缓存，最后写延后块并给出每张画布的来源行（`Provenance`）与汇总。瓦片缺了就 `NeedTile`，驻留的就 touch，缓存看到的使用顺序与原来一致。Rust 引擎。
- `src/engine/reveal_host_tests.rs` — 原生宿主测试：页面在固定悬浮按钮下滚动，合成器把按钮烧进了画布；同步宿主只经公开 API、在四块的小缓存上跑完四遍，页面逐像素恢复，来源行指向后来的帧。Rust 引擎测试。
- `catalog/zh.json`、`catalog/en.json` — `src/i18n` 的 `diag`、`progress`、`names` 三节的导出（`deno task export-catalog`）；`tests/unit/catalog-export.test.ts` 在它们与 TS 目录不一致时失败。生成文件。

### rust/long-screen（原生驱动与命令行，§十三第 7 步）

原生宿主：与 `src/pipeline/*` 同序、同样地驱动引擎的各个会话，持久化的每一行与网页逐行相同（键、字段顺序、`<run>` 之外的值都相同，见 `test-results/native-cli/`）。它是唯一发布的 crate：根是驱动 API，算法核心（`src/kernels`）、引擎（`src/engine`）和原生解码（`src/decode`）都是它的模块。在工作区的 `default-members` 里，所以普通的 `cargo` 命令带着它的原生默认 feature；面向 wasm32 的命令要加 `--no-default-features`。

crates.io 只发布这一个 crate（维护者 2026-10-11 的决定：核心和引擎是没人单独用的实现层，一个名字集中下载量和依赖方，第一次手动发布和可信发布也只要做一次）。`crates-v<版本>` 标签触发 `.github/workflows/release-crates.yml`，经可信发布；第一个版本要维护者手动发，见 `docs/RELEASING.md`。`long-screen-wasm`、`long-screen-bench`、`long-screen-py` 不发布。crate 带英文 `README.md`（示例经 `cargo test --doc` 编译）和 `LICENSE`，`include` 只放构建需要的文件（另带引擎的 `catalog/*.json`）。根是驱动 API（`run`、`Options`、`RunResult`、帧源……）；`kernels`、`engine`、`decode` 是公开的模块，但属于实现层，API 在次版本之间可能变（`test-results/crates-release/`、`test-results/one-crate/`）。

feature：默认全开。`cli`（命令行与 clap，含 `driver`、`decode`）、`driver`（根上的驱动 API，含 `catalog`）、`decode`（`decode` 模块与 `VideoSource`，解码选项在根上重新导出为 `DecodeOptions`/`DecodeBackend`；macOS 的 objc2 与 Windows 的 windows 依赖仍按目标平台限定）、`rayon`（核心的 `pool::par_for` 走 rayon 线程池；关掉时驱动在调用线程上跑，`threads` 大于 1 报 `Error::Threads`）、`catalog`（引擎的 zh/en 目录，需要 serde_json）。`default-features = false` 只剩 `kernels` 与 `engine`，就是 `rust/wasm` 用的形状；`rust/python` 要 `driver`、`decode`、`rayon`，`rust/bench` 要 `driver`、`rayon`。第三方依赖用版本范围，只有结果依赖其确切输出的 `png` 与 `libm` 用 `=` 钉住。

- `src/lib.rs` — crate 入口：模块声明、feature 门控、crate 文档（驱动示例、各层与 feature 的说明），以及把 `driver.rs` 的公开项和解码选项重新导出到根上。原生宿主。
- `src/driver.rs` — 公开 API（`driver` feature）：`run(source, options, observer, control) -> Result<RunResult, Error>`、`Options`/`Settings`（网页 `Settings` 的默认值）、`Observer`（进度与诊断回调）、`Control`（跨线程的暂停与停止，在步与步之间检查）、`Progress`/`Diagnostic`；`--threads` 用 `rayon::ThreadPool::install`，不改全局线程池。顺序编排（启动诊断、六个阶段、失败处理、`performance` 行）对应 `src/pipeline/engine.ts`。原生宿主。
- `src/context.rs` — `RunContext` 与 `Diagnostics` 的对应：项目行、诊断日志（`diagnostic/<序号>`、按代码计数与最高 severity）、进度节流、暂停/停止状态机（`stopped`/`partial`/`honourStop` 与网页一致）。日志行一律写 zh 文字（与网页逐字节相同），给观察者的是所选语言（默认 en）。原生宿主。
- `src/scan.rs`、`src/solve.rs`、`src/render.rs`、`src/reveal.rs`、`src/present.rs` — 各阶段的宿主，逐个对应 `src/pipeline/scan.ts`、`solve/solve.ts`（含 `solve/diagnostics.ts` 的逐代码字段顺序）、`render.ts`（单帧前瞻、1.2 s 周期落盘）+ `src/core/compositor.ts`、`reveal.ts`、`presentation.ts` + `src/core/framing.ts` + `TileStore.buildPyramid`，也包括 `src/core/wasm/*.ts` 里决定行形状的解码（运动场的两种字段顺序、区域行的命名与字段顺序）。`scan-features/` 与 `keyframe/` 是求解结束就删的暂存，原生宿主只放在内存里，不进存储。揭示的 `NeedMemory` 原生一律回答“放得下”：网页那 128 MB 余量和 2 GB/4 GB 上限是 wasm 堆的限制，原生进程没有，所以网页会以 `REVEAL_SKIPPED` 跳过的超大运行，原生照样揭示。原生宿主。
- `src/tiles.rs` — `TileStore` 的对应：瓦片缓存换出与落盘、PNG 编解码（`png` crate，与 `rust/wasm/src/png.rs` 相同的 `Compression::Fast` 设置，字节相同；这几行编码设置是有意的重复）。原生宿主。
- `src/store.rs` — 行存储：按键排序的内存表（与 `MemoryKV` 的遍历顺序相同）；可设内存预算，超出后已编码的瓦片 PNG 写到临时目录。原生宿主。
- `src/value.rs` — 行的值：保持字段插入顺序的 JS 值（类型化数组、Blob），`JSON.stringify` 的数字与字符串写法、JS 的 `toFixed`/`toLocaleString`，以及 `scripts/fingerprint-scenarios.ts` 的规范化与摘要（`RunResult::fingerprint`）。原生宿主。
- `src/source.rs` — `FrameSource`：每一遍重新解码一次（与网页相同；整段缓存原生尺寸的帧对 3456×2234 的录屏每帧 31 MB，放不下），`sparse_frames` 让揭示阶段不转换它不读的帧。`VideoSource`（`decode` feature）经 `src/decode` 解码，YUV→RGBA 用核心的 `yuv::convert`，10 位 PQ/HLG 先经 `Frame::to_8bit` 取整成 8 位再走核心的 HDR 路径（高精度路径是以后的改进）；`RawSource` 回放现成的 RGBA 帧。原生宿主：I/O。
- `src/output.rs` — `RunResult`：画布列表（`CanvasInfo.name` 是存下的 zh 名称，`display_name()` 给运行语言下的名称）、主图（有呈现画布时取呈现画布）与片段、按瓦片带逐行读出任意尺寸的画布（`read_rows`，PNG 和 Python 的 NumPy 数组都用它）、流式写 PNG、行指纹。原生宿主：I/O。
- `src/bin/long-screen.rs` — 命令行（`cli` feature，clap）：进度与警告写 stderr，`--json` 报告，退出码 0 完成、3 部分结果、1 失败、2 参数错误、4 打不开视频（含缺 ffmpeg 时 `src/decode` 给的安装提示）、5 写不出文件。网页的完整结果包（ZIP、离线查看器）没有搬过来：它在 `src/export/` 的 TS 里，体量不小，留作以后的工作。
- `src/decode/mod.rs` + `{avf,mf,ffmpeg}.rs` — 原生解码（`decode` feature）：文件第一条视频轨的每一帧按展示顺序、带容器给的时间戳交出一次，不重采样（录屏是可变帧率）；保留解码器自己的 4:2:0 平面（8 或 10 位）、色彩标记和编码方向（`VideoInfo::rotation`）。后端：macOS 的 AVFoundation、Windows 的 Media Foundation，以及各平台都能用的用户自装 `ffmpeg`/`ffprobe` 子进程（Linux 只用它，其他系统打不开时回退到它）。`tests/decode.rs` 是各后端的端到端检查，`examples/probe.rs` 打印一个文件的元数据与帧时间。原生宿主：I/O。
- `examples/parity.rs` — 一致性测试：读 `scripts/native-parity.ts export` 导出的合成场景帧，或像 `scripts/native-parity.ts recording` 那样用 ffmpeg 解码录屏，输出与 `scripts/fingerprint-scenarios.ts` 同格式的指纹，用 `scripts/compare-fingerprints.ts` 比较。
- `tests/driver.rs` — 原生端到端：在这里生成的纹理页面滚动 24 帧，先测失败（没有帧、瓦片尺寸非法、停止、中途变尺寸），再测结果（主图逐像素等于页面、PNG 输出、1 线程与 4 线程逐行相同）。

### rust/python（Python 包，§十三第 8 步）

PyO3 绑定（`long-screen-py`，cdylib，导入名 `long_screen._native`；依赖 `long-screen` 的 `driver`、`decode`、`rayon` feature，不带命令行），只有胶水代码：把 Python 参数换成 `rust/long-screen` 的 `Options` 和帧源，释放 GIL 调 `long_screen::run`，再把结果的画布交成 PNG 文件或 NumPy 数组。PyPI 发行名 `long-screen`（2026-10-10 无人占用），abi3 轮子支持 CPython 3.11 起：3.11 是缓冲区协议进入稳定 ABI 的第一个版本，帧可以不经 NumPy 的 C API 直接交给引擎；3.10 在 2026 年 10 月停止维护。用 maturin 构建（`pyproject.toml`），不在工作区的 `default-members` 里。

- `src/lib.rs` — 模块、`reconstruct(path, …)`、异常（`LongScreenError`、`DecoderError`、`DecoderMissingError`、`RunFailedError`）与 `Progress`。进度回调和 Ctrl-C 检查都在 `Observer::progress` 里重新拿 GIL：回调返回 `False` 经 `Control::stop` 停下并保留已完成的部分；回调抛出的异常与 Ctrl-C 也先停下运行，等它在下一步收尾后再抛出。绑定层：Python。
- `src/frames.rs` — `reconstruct_frames(frames, width=, height=, …)`：可重复迭代的对象（列表等）每一遍重新读一次，每帧拿一次 GIL、经缓冲区协议复制；一次性的迭代器（生成器）先写进临时文件，再按 `RawSource` 读。帧的时长取下一帧时间戳之差（与 `VideoSource` 相同）。`_fingerprint_raw` 是测试钩子：像 `examples/parity.rs` 那样跑一个导出的合成场景，给出行指纹。绑定层：Python。
- `src/result.rs` — `Result`（status、diagnostics 字典、`save`、`print_image`、`print`/`fragments`/`canvases`）与 `Canvas`（`save`、`image`）；`_fingerprint()` 是测试钩子。绑定层：Python。
- `python/long_screen/` — 包本身：`__init__.py` 重新导出扩展模块，`_native.pyi` 类型存根，`py.typed`。
- `tests/` — pytest：合成页面上的 `reconstruct_frames`（主图逐像素等于页面、生成器与列表逐行相同、线程数无关、各种坏帧）、停止（回调返回 `False`、回调抛异常、真实的 SIGINT）、test_3 和 test_7 上与 `long-screen` 命令行的 PNG 像素哈希与字节相同、打不开视频的几种错误。`parity_scenarios.py`、`parity_recording.py` 与 `examples/fingerprint.rs` 用来量扩展模块与可执行文件、网页的逐行一致性。`deno task test:python`（`scripts/test-python.sh`）构建轮子、装进新的虚拟环境再跑。
- `README.md` — PyPI 上的说明（英文）。`.github/workflows/python.yml` 在 `py-v<版本>` 标签上构建 macOS（arm64、x86_64）、Linux（manylinux x86_64、aarch64）、Windows 的轮子和 sdist，经可信发布（trusted publishing）上传 PyPI。Linux 轮子运行时要用户自己装 ffmpeg；Windows 用系统的 Media Foundation。

### src/pipeline（编排 + 尚未迁移的算法转发）

- `engine.ts` — `Engine`：一次重建运行的公开门面，`run()` 编排（阶段顺序、计时、性能行、终态、资源释放）。TS 外壳：编排。
- `context.ts` — `RunContext`：每趟共享的状态与服务，存储/诊断/进度/暂停/停止管线。TS 外壳：编排。
- `scan.ts` — 扫描趟的宿主：解码循环、把帧拷进引擎的扫描会话、WebGPU 灰度图、按 24 行一批落盘、宿主才知道的事实（计算后端、帧转换、帧参照图）、用目录把会话的结构化诊断排成文字、失败分类、进度与停止。算法都在 `rust/long-screen/src/engine/scan.rs`。TS 外壳：编排。
- `reveal.ts` — 揭示阶段的宿主：驱动引擎的 `RevealSession`，回答内存检查（`canAllocate` 加 128 MB 余量）、读观察台账、按会话要的顺序载入瓦片、每遍解码一次录屏并按 `wanted` 只转换要读的帧（在 CPU 上转换的运行里，帧以 YUV 平面交来，直接转进会话的帧缓冲，省掉 RGBA 拷出再拷回的两次整帧拷贝）、写 `reveal/<canvas>` 来源行、`REVEAL_SKIPPED` 诊断行与 `reveal-summary`，计时、进度、暂停与停止。TS 外壳：宿主。
- `presentation.ts` — `run()` 在 scan/solve/render/揭示之后驱动的 framing 与 pyramid 展示阶段：逐画布调用 `buildFramedCanvas` 与 `TileStore.buildPyramid`（两者是引擎 `FramingSession`/`PyramidSession` 的宿主），发进度与诊断，在画布之间响应停止；本身不含算法，失败只降级为警告诊断。TS 外壳：编排。
- `render.ts` — 渲染趟的宿主：单帧前瞻解码循环，按引擎渲染会话（`rust/long-screen/src/engine/render.rs`）的要求读 plan、相邻帧的一致性记录、`canvas/` 行、瓦片与时间记录，把帧像素写进会话的帧槽，按原来的节奏写观察台账、画布元数据与瓦片，格式化诊断、报告进度，处理 MISSING_PLAN、存储失败分类、暂停/停止与帧数不符。TS 外壳：编排 + I/O。
- `consistency.ts` — `consistency/<frame>` 行的类型（solve 写、渲染会话读），以及 `consistencyMask()`：同一 Rust 内核加上画布身份闸门的独立入口，渲染不再调用它，留给 parity 测试与基准。TS 外壳：绑定转发。
- `solve/solve.ts` — 求解趟的宿主：解码循环、每帧读 scan 记录与存储的特征、按会话要求读回关键帧行、把会话交回的行按序落盘（计划与一致性行每 24 行一批）、诊断文字、进度/暂停/停止、前缀失败分类、帧数核对、位置图松弛与临时行删除；求解本身在 `rust/long-screen/src/engine/solve/`。TS 外壳：I/O + 编排。
- `solve/diagnostics.ts` — 把会话的诊断事件按目录格式化成一直以来存的诊断行（字段顺序按各条原样）。TS 外壳：文案。

### src/package（TS 外壳：npm 包）

让别的网页也能跑重建（§十三第 8 步的 TS 部分）。包就是应用自己的 worker、三个核心构建和两个辅助 worker，原样打包，外加一个在页面这一侧驱动它们的入口；没有任何算法，也不复制引擎逻辑。

- `index.ts` — 入口 `reconstruct(source, options)`：每次调用新建一个 worker（`new URL('./worker.js', import.meta.url)`），先发 `locale` 和 `storage` 消息，再用应用同一套命令跑完（`start` → 等 `finished` → 翻页读 `canvases`、`diagnostics` → 每张可用画布 `export` 成单张 PNG），返回 `{ result, pause, resume, stop, cancel }`。画布的筛选和排序与应用画布菜单一致（呈现画布在前，再移动内容、固定部分，各按观察像素数），已经接回别处的片段不导出。worker 写进 OPFS 的临时 PNG 先读进内存再删掉，因为条目删除后原来的 `File` 就读不了了。TS 外壳：编排。
- `types.ts` — 公开类型，只有声明、不 import 任何东西，构建时原样当作 `index.d.ts` 发布；`index.ts` 在编译期检查它们与 worker 实际发出的诊断、进度和 `reconstruct` 的签名一致。TS 外壳（类型定义）。
- `README.md` — 包自己的说明（英文）：安装、示例、文件怎么服务、跨源隔离、许可。

存储：库不沿用应用「保留最近一张 24 小时」的规则。那条规则是给有界面的应用防刷新和崩溃的，库没有可以恢复到的界面。每次调用用自己的 IndexedDB 数据库（`long-screen-package-<uuid>`，`protocol.ts` 的 `PACKAGE_DB_PREFIX`），`result` 落定之前删掉，成功、出错、`cancel()` 都一样；这样 worker 在 `start` 时的清扫也碰不到同源的应用自己的数据库。调用期间持有 Web Lock `long-screen-package:<库名>`；页面中途关掉留下的库，由同源下一次调用删掉（没有锁持有的才删）。不用内存 KV：长录屏的中间记录可能有几百 MB，应用正是为此才把它们放进 IndexedDB。

打包路线：不用 `@deno/dnt`。dnt 把模块树逐文件转成 npm 模块，处理不了 worker 必须是单个自足文件、以及 worker 按 `new URL('./x', import.meta.url)` 去取的那些同级文件（三个 `.wasm`、`core-helper.js`、`convert-worker.js`）。`scripts/build-package.ts` 沿用应用构建的 `deno bundle`，产出一个扁平目录，npm 发布的就是这个目录。所有文件引用都是字面量 `new URL('./文件', import.meta.url)`，Vite 和 webpack 会自己发出这些文件（用 Vite 8.3.4、webpack 5.111.1 构建的使用者页面在 Chrome 和 WebKit 里跑通过，PNG 与应用的相同）；为此 `loader.ts` 给每个核心构建写了自己的字面量（`coreURL`）。esbuild 和 `deno bundle` 不处理这种 URL，要把包里的 `*.js`、`*.wasm` 复制到打包结果旁边；Vite 开发服务器要 `optimizeDeps.exclude`。

### src/i18n（TS 外壳：界面语言）

- `index.ts` — 本 JS 环境（页面、每个 worker、Deno 各一份）唯一的 i18next 实例与有类型的 `t()`；目录内联打包，同步初始化；默认 zh，从不读取 `navigator`。TS 外壳：UI。
- `page.ts` — 仅页面：加载时选语言（已保存的选择 → 浏览器首选语言 → 英文，任何 zh-* 都选 zh）、按 `data-i18n*` 属性翻译静态页面、语言菜单保存选择并重新加载（打开中的项目在重新加载后重新打开）。检测本身不保存任何东西。TS 外壳：UI，兼 I/O（localStorage）。
- `names.ts` — 持久化的 zh 区域/画布名称词表到界面语言的显示映射，及手动区域的规范名称；原生一侧的同一映射是 `rust/long-screen/src/engine/catalog.rs::display_name`。TS 外壳：UI。
- `catalog.ts`、`zh/*.ts`、`en/*.ts` — 目录。按显示位置分为 `page`（静态页面）、`ui`（页面脚本）、`pipeline`（worker 写出的诊断、进度、导出文本）；每个 en 分区的类型由对应的 zh 分区导出，缺键或多键是编译错误，`tests/unit/i18n.test.ts` 再检查插值变量一致、英文无汉字、静态页面引用的键都存在。TS 外壳（数据）。

### src/media（TS 外壳：浏览器 API / I/O）

- `source.ts` — `FrameSource` 实现的组装点：demuxer 选择、`FrameConverter` 接入、缓冲区释放；兼容模式的 `CompatibilitySource` 对 HDR 录屏读截图的编码值交给核心换算。TS 外壳：编排 + 浏览器 API。
- `capture.ts` — `<video>` 当前帧的截图：按页面显示的颜色，或（HDR 录屏）不做颜色转换的编码值。不查 DOM，测试工具包也能用。TS 外壳：浏览器 API。
- `reader.ts` — `Demuxer`/`Packet` 接口，以及 `BlobReader`：最多 8 个 256KiB 页面的随机访问读取，不调用整段 `arrayBuffer()`；现在只被 `isobmff-probe.ts` 使用（容器本身的读取交给了 mediabunny 自己的 `BlobSource`）。TS 外壳：I/O。
- `mediabunny-demux.ts` — `MediabunnyDemuxer`：MP4/MOV/fMP4/WebM 解封装，包在 npm 包 mediabunny 的 `Input`/`BlobSource`/`EncodedPacketSink` 之上，只用它的 packet 级 API（不用它的解码 sink，解码仍是本项目自己的 WebCodecs 路径）；把 mediabunny "警告后继续"的几种情形翻译成本项目原有的、冻结的错误文案。TS 外壳：I/O（容器解析）。
- `isobmff-probe.ts` — 一次轻量 box 扫描，只检测 mediabunny 自己不拒绝的几种情形（多重/变速剪辑列表、sample-description 索引 ≠ 1）与 mediabunny 没有对应诊断的版本 0 `ctts` 有符号偏移，以及文件在 `mdat`/`moof` 中途结束（`TRUNCATED_RECORDING` 警告；mediabunny 会不声不响地读到最后一个完整样本为止）；顶层 box 的容错与 mediabunny 一致（解析不了或超出文件末尾的顶层 box 结束扫描而不报错），不比它更严；不重复 mediabunny 的解封装本身。TS 外壳：I/O（容器解析）。
- `sniff.ts` — 按文件前 512 字节判断所选文件是什么：ISOBMFF（MP4/MOV）与 EBML（WebM/MKV）放行；文本、图片（含 HEIC/AVIF）、PDF、压缩包，以及 AVI/WMV/FLV/MPEG-TS/GIF 等本项目不读的视频格式，由 source-file.ts 直接拒绝并说明原因。认不出的字节只在文件名或类型表明是视频时放行，交给 demuxer 判断。TS 外壳：I/O。
- `convert.ts` — `VideoFrame` → RGBA 转换的可注入形态（直转/worker 转换/平面转换）与显式释放缓冲池接入。TS 外壳：浏览器 API（WebCodecs）。
- `convert-worker.ts` — 帧转换 worker：在转移进来的 `VideoFrame` 上首帧决定用 WebGPU 还是 `copyTo({format:'RGBA'})`，之后整段用同一种，转移 RGBA 缓冲回去；首个 worker 选定 `copyTo` 时，`workerConverter` 会再开最多两个只用 CPU 的 worker 分担（同一个浏览器调用，像素相同）；在 `copyTo` 给不出 RGBA 的浏览器（Safari）里，平面路径通过首帧检查后由 worker 拷出每帧的原生平面（Safari 上这一步同步阻塞调用线程），流水线线程再用同一个核心转换；刻意保持零依赖（不引入 `src/core/wasm.ts`）。TS 外壳：浏览器 API（Worker）。
- `gpu-convert.ts` — WebGPU 帧转换：平面拷出、上传、只做 YUV 矩阵的计算着色器、映射回读；首帧与后备转换比对并计时（§四）。TS 外壳：浏览器 API（WebGPU）。
- `conversion-check.ts` — 帧取哪个 YUV 矩阵、一种转换的首帧要多接近另一种才能接管整段；零依赖，供 worker 与主线程共用。TS 外壳：浏览器 API（WebCodecs）。
- `rgba-copy.ts` — `copyTo(RGBA)` 选项与结果布局校验，供直转/worker 转换器与 convert-worker.ts 共用。TS 外壳：浏览器 API。
- `pool.ts` — 显式释放的 RGBA 转换缓冲池：`release()` 才归还，永不按固定轮转回收。TS 外壳：I/O（内存管理）。
- `demo.ts` — `DemoSource`：内置 demo 复用与测试套件相同的 ground-truth 合成场景。TS 外壳：编排（测试/演示数据接入）。

### src/codec、src/export、src/storage、src/synthetic（TS 外壳，各自领域）

- `codec/crc.ts` — 一次性 `crc32()`，经 Rust `crc32fast` 的薄封装：`codec/png.ts::chunk()` 唯一的生产调用方总是先把类型+正文拼成连续内存，不需要增量（分批喂数据）形式；旧的 handle 表 + `FinalizationRegistry` 增量 CRC（`ls_crc32_new/update/digest/free`）已删。绑定转发层。
- `codec/png.ts` — 单 PNG chunk 编解码：chunk 组装、`decodePNG`/`encodeRGBA`，调用核心 (un)filter 与 CRC。TS 外壳：I/O（编码），部分绑定转发。
- `export/zip.ts` — `ByteSink` 接口与 `client-zip`（npm，ZIP64）驱动的写入。TS 外壳：I/O。
- `export/target.ts` — 同步文件写入目标的小接口与实现（`createId` 用于临时命名）。TS 外壳：I/O。
- `export/project.ts` — 完整项目 ZIP64 导出：画布/瓦片/诊断从 KV 读出并交给 `ZipWriter`。TS 外壳：编排 + I/O。
- `export/png.ts` — 从磁盘瓦片流式产出原生分辨率行，未观察像素透明。TS 外壳：I/O。
- `export/crop.ts` — 裁切矩形的整像素换算：画布导出覆盖的整像素范围、把用户的矩形取整并夹进画布（什么都不剩就拒绝）、判断是否等于整张；`exportCanvas` 的单图/分页按它取范围，worker 存 `crop/<canvas>` 行之前也用它校验。只有矩形算术，不碰像素。TS 外壳：I/O 参数。
- `export/offline.ts` — 生成自包含 `file://` 离线查看器 HTML。TS 外壳：I/O（静态资源生成）。
- `storage/db.ts` — `KV`/`Row`/`Database`/`MemoryKV`/`Namespace` 等存储抽象与遍历/前缀删除工具。`Database.open()` 默认打开应用唯一的 `long-screen-local`，npm 包的每次调用传入自己的库名。TS 外壳：I/O。
- `storage/tiles.ts` — `TileStore`：引擎瓦片缓存（`rust/long-screen/src/engine/tiles.rs`）的宿主——读回并解码引擎要的瓦片、把换出与 flush 的瓦片编码成 PNG 写进 `tile/`、`tile-index/` 行；`get()` 交出的瓦片是核心内存的视图（每次读取都重新取，换出后自动换成一份 JS 拷贝）；`saveResident(id)` 存下引擎会话按缓存 id 交回的瓦片；`buildPyramid()` 是引擎金字塔会话（`rust/long-screen/src/engine/pyramid.rs`）的宿主：读它要的 `tile-index/` 与子瓦片行、写它交回的父瓦片行和每层后的画布行、维护 `pyramid-todo/` 行。TS 外壳：I/O。
- `storage/diagnostics.ts` — 诊断事件的存储形态、按代码取最高严重级别。TS 外壳：I/O。
- `storage/projects.ts` — 项目键布局（`project/`、`run/<id>/`，以及旧版写过的 `project-index/`）的唯一入口：删除一个项目，以及 `sweepProjects` 只保留屏幕上那张结果、删掉其余一切（应用不保留历史）。TS 外壳：I/O。
- `synthetic/world.ts` — `World`：无损程序化页面，用于可精确核验的合成场景。TS 外壳：编排（测试基础设施）。
- `synthetic/scenarios.ts` — 24 个合成场景目录的构建（`buildScenario`）与期望值。TS 外壳：编排（测试基础设施）。
- `synthetic/source.ts` — `ScenarioSource`：合成场景的 `FrameSource` 封装，Deno 与浏览器行为一致。TS 外壳：编排（测试基础设施）。
- `synthetic/verify.ts` — 重建结果与合成 ground truth 的逐像素核验，含瞬态/污染像素的可恢复性分类。TS 外壳：编排（测试基础设施）。

### 顶层与其它（src/*.ts）

- `types.ts` — 跨模块共享的纯数据类型（`Gray`/`RGBA`/`Region`/`CanvasMeta` 等），无逻辑。TS 外壳（类型定义）。
- `protocol.ts` — 页面↔worker 类型化协议：冻结的命令名字符串 + 每个命令的载荷/回复类型，以及命令之前发的 `locale`、`storage` 两条消息（`storage` 只有 npm 包发，指定这次调用自己的数据库）。TS 外壳：worker RPC。
- `rpc-client.ts` — 一个 worker 的有类型 RPC 客户端：按 id 配对的请求/回复、`WorkerEvent` 订阅、worker 死掉时拒绝所有未回复的请求。应用页面用一个（`ui/rpc.ts`），npm 包每次调用用一个。TS 外壳：worker RPC。
- `worker.ts` — worker 入口：接线 `Engine`、存储、项目生命周期、媒体源选择到 `protocol.ts` 的命令处理器。应用和 npm 包用的是同一个 worker。TS 外壳：worker RPC + 编排。
- `device-check.ts` — 独立页面（不随主应用加载）：报告本机/本浏览器的核心能力与 GPU 路径成本。TS 外壳：编排（诊断工具）。
- `sw.ts` — service worker（构建成站点根目录的 `sw.js`，作用域是整个应用），让装好的 App 断网也能打开、能跑。网络优先：有网时每个请求照旧走网络并重新验证（`_headers` 的 `no-cache`），推到 main 的新版本下次打开就到；网络失败或 4 秒内没回响应头时才用缓存。缓存一次存一整个构建：`scripts/build.ts` 把运行要用的全部文件清单和内容哈希写进 `sw.js`，安装时按哈希存进 `long-screen-<哈希>`，激活时删掉旧构建的缓存；不调用 `skipWaiting()`/`clients.claim()`，已打开的页面一直用加载它的那个构建。要整个关掉：把 `install.ts` 的注册换成注销已有注册（`navigator.serviceWorker.getRegistrations()` 逐个 `unregister()`），有网的访客下次打开就生效；万一是 service worker 本身坏了、页面打不开，再把 `sw.ts` 换成只做清理的版本（`install` 里 `skipWaiting()`，`activate` 里删掉 `long-screen-*` 缓存后 `registration.unregister()`，不处理 `fetch`），浏览器打开页面时会比对 `sw.js`，换上它就自行清理。TS 外壳：浏览器 I/O。
- `testkit.ts` — 浏览器测试用：把 `Engine`/`Database`/`PoseGraph`/`RegionAtlas`/`TileStore` 等挂到 `window` 上给 Playwright 用，不随应用加载。TS 外壳（测试基础设施）。

## 十三、Rust 引擎库：边界与迁移

目标：把 `src/pipeline/` 里的流程搬进 Rust，让一个 crate 自己就能从一串帧得到长截图；网页、命令行、桌面版和 Python 共用同一份引擎。§三的原则不变（算法在 Rust，TS 只做外壳），变的是“外壳”的范围：今天的 TS 外壳还负责三遍的顺序、逐区域的追踪状态机和记录的组装，迁移之后这些都在 Rust，TS 只剩解码、存储、界面和驱动引擎的循环。

### Crate 划分

- `long-screen`（`rust/long-screen`，库名 `long_screen`，可执行文件名 `long-screen`）：唯一发布的 crate。根是原生驱动库（命令行、桌面版、Python 共用，`driver` feature）加命令行（`cli` feature）；下面三层是它的模块：
  - `kernels`（`src/kernels`）：算法本身，没有 FFI，没有 I/O。
  - `engine`（`src/engine`）：一次运行的状态机——scan、solve、render、reveal、framing、金字塔，以及诊断和持久化记录的类型。不做 I/O，不读时钟。
  - `decode`（`src/decode`，`decode` feature）：原生解码（macOS AVFoundation、Windows Media Foundation、其他平台调用用户自己安装的 ffmpeg）。
    这三层原来是 `long-screen-core`、`long-screen-engine`、`long-screen-decode` 三个 crate（`rust/core`、`rust/engine`、`rust/decode`），2026-10-11 并进 `long-screen`，只发布一个名字（`test-results/one-crate/`）。模块名用 `kernels` 而不是 `core`：crate 根上叫 `core` 的模块会和内置的 `core` crate 同名，`use core::…` 从此有歧义。
- `long-screen-wasm`（`rust/wasm`）：cdylib，浏览器用的 `extern "C"` 导出（原来的 `rust/core/src/abi`），以 `default-features = false` 依赖 `long-screen`，只覆盖 `kernels` 和 `engine`；三种构建（scalar、SIMD、threads）都从它出。
- `long-screen-py`（`rust/python`）：PyO3 绑定。
- `long-screen-bench`（`rust/bench`）：基准测试，不发布。

### I/O 边界：引擎不做 I/O，由宿主一步一步驱动

- 引擎从不 await，也不回调宿主。每一遍是一个会话对象（`ScanSession`、`SolveSession`、`RenderSession`……）。宿主每次喂一帧（`push_frame`），会话返回这一步产生的效果：要写入或删除的记录、诊断事件、处理到第几帧。宿主负责落盘、发事件，并在两步之间检查暂停和停止。原生宿主是一个同步循环；网页宿主是现在的 TS 循环，两步之间照常 await IndexedDB。
- 引擎今天从存储读回的东西，改为宿主在调用时一并传入：solve 的一步收到这一帧的 scan 记录和特征，render 的一步收到这一帧的 plan 和前后的一致性记录。这样浏览器的内存占用和今天一样（中间记录照旧写进 IndexedDB），原生宿主则可以全部放在内存里。
- tile 超出内存预算被换出后要读回时，用“先声明、后提供”两步：`needs(frame)` 返回缺的 tile 键，宿主取回后 `provide`，然后才 `push_frame`。原生宿主在同一线程里同步完成。
- 一次就要很久的步骤（位姿图松弛、金字塔、reveal）拆成可以分段调用的形式（每次 N 轮迭代或 N 个 tile），暂停和停止在两段之间生效。
- 时间节流（每 100 ms 报一次进度、每 1.2 s 落一次盘）是宿主的事。引擎只报告处理到哪一帧、哪一阶段。
- WebGPU 灰度是网页外壳的加速选项：会话接受宿主已经算好的分析灰度图，没有就自己算。
- 多线程：wasm 继续用 `pool.rs`；原生用 rayon（`long-screen` 的 `rayon` feature，`pool::par_for` 在调用所在的 rayon 线程池里分块），沿用“结果与线程数无关”的契约：原生 1 线程与默认线程数的场景指纹逐行相同。

### 持久化记录

- 记录的键和值形状不变（`docs/FORMAT.md`），指纹可以逐行比较。Rust 定义记录类型，经现有的 `wire` 编码交给 TS，TS 解码成和今天完全一样的 JS 对象再写进 IndexedDB；原生宿主直接拿 Rust 值。
- 键名、批量提交的节奏（每 24 行一批）、删除中间记录的时机都跟今天一致，除非某次迁移明确说明改了什么、为什么改，并解释受影响的指纹行。

### 诊断

- 引擎只发结构化事件：code、severity、参数、frame/time、detail，不带文字。
- 文字由宿主按目录格式化。网页用现有的 zh/en 目录，持久化的仍是 zh 文字，字节不变。原生宿主用同一份目录：构建时从 `src/i18n` 导出 JSON，嵌进 `long-screen` crate（`catalog/*.json`，引擎的 `catalog` 模块），并有测试检查它与 TS 目录同步。

### 桌面版需要的接口（现在就留出来，不要事后补）

进度事件、暂停与取消、内存预算、预览逐步更新（金字塔按画布增量刷新）、结果直接写到磁盘、诊断可以按 code 过滤。

### 每一步怎么验证

- oracle 是迁移前的树：迁移前用 `scripts/fingerprint-scenarios.ts` 存下全部合成场景的指纹，迁移后在 scalar、SIMD、threads 三种构建上逐行比较。凡有不同，必须由这次迁移解释。GPU 两边都固定为 `null`。
- 被迁移的是编排，不是单个函数，所以整条流水线的逐行指纹就是最强的 oracle，不再逐个冻结 TS 文件。仍能脱离 Engine 单独调用的纯函数，照旧冻结到 `tests/support/reference/` 并写 parity 测试。
- 最后在 `test_case/public_test_cases` 上做真实录屏 A/B（tile 哈希和诊断计数），并跑浏览器测试；与干净 main 的已知失败对照。
