> **历史文档。** 写于 `feat/map-reconstruction-optimization`（PR #8）完成时，基准是这批改动前的 main `7dd7a38`。数字反映当时的状态，不是当前基线；现行规则以 [ARCHITECTURE.md](../ARCHITECTURE.md) §十 为准。文中提到的测量产物在作者本机 gitignored 的 `test-results/`（`pro-review-20261014/`、`map-trials-20261014/`、`map-content-20261015/`、`optimization-completion-20261016/`、`review-fixes-20261017/`），不在仓库里。索引见 [README.md](README.md)。

这一轮从 [issue #7](https://github.com/t41372/long-screen/issues/7) 的 Apple Maps 录屏出发：原算法跑得完，却拼不成一张地图。修好追踪后，又处理了地图标签与控件残影、HDR 转色耗时和一批外部 review 提出的候选。这里只留下以后还用得上的东西：根因、采用的做法、试过但排除的路线，以及还没解决的问题。

## 起点：Apple Maps 录屏

素材是 2272×1760、SDR H.264、1,644 帧的 Apple Maps 平移录屏（私人素材，未加入 Git）。原算法得到 140 个非空移动画布；`UNPLACED_FRAGMENT` 90 条、`SCALE_CHANGE_FRAGMENT` 49 条，reveal 估算需要再加 2,448 MB 而被跳过。管线约三分之二的时间花在 140 个碎片的 framing／pyramid 上。

- **不是缩放。** OpenCV LK＋similarity RANSAC 独立检查全部 1,643 个相邻帧对，每步 scale 在 0.999710–1.000225 之间，旋转小于 0.02°。49 条 scale 诊断都来自追踪失败之后的 `probe_scale`，它只比较非单位尺度，没有和单位尺度在同一批像素上比较。
- **正确平移已在候选里，却被拒绝。** 一是自动学到的区域包含比例尺、右侧按钮等固定 UI，原生采样偏向强梯度，固定白字的误差（约 42–50）把移动地图的分数拉高。二是低对比地图上的亚像素相位：sampling-insensitive rescue 要求 winner < 14 且 runner-up ≥ 14，而这些步骤的 runner-up 只有 9–11。用单张真实地图帧生成的纯平移对照，半像素位移的原生误差就有 19.57，证明相位本身足以触发拒绝。
- **只把区域手动设成地图内部**，非空片段 140 → 3，但裁掉了合法的地图边缘，只能当对照。由此得出的方向是：把「拿来验证位置的支持区」和「可输出的内容范围」分开。

## 采用的改动

### 追踪：相位救援与独立的配准支持区

- 原有判据拒绝后，新增低对比相位救援：insensitive winner < 8、对手 > 2×winner 且至少高 4；analysis audit overlap ≥ 0.5、agreement ≥ 0.8、至少 12 个 agreeing blocks；至少 24 个支持同一位移的 unique matches，分布在 4×4 网格至少 6 格、跨越两轴至少 40%。相距超过 2 px 而原生误差接近的候选仍会阻止救援。全局的 14 没有调高。
- 只有在本来要开新片段、而且真的用上了新救援时，才为该区域启用 registration support。支持区取当前 feature 范围，排除空白 capture padding，再把短边内缩 10%；特征不足 64 个或覆盖范围不够时不启用。提前启用（即使救援没被使用）会改变后续追踪，已实测排除。
- odometry、anchor、drift、relocalization 共用同一支持区；`roi` 保持完整区域的原点，另存 `registration_rect`。大步长只剩边缘可见时，内部 odometry 失败且没有救援，才用完整区域重试（420 px 薄重叠跳转的测试先失败，补上后通过）。
- 新救援保留 `LOW_CONFIDENCE_PLACEMENT`，detail 里记录 registration 与 output 的屏幕矩形，实际用到全区回退时另记一项。

完整地图：非空移动画布 140 → 1，`UNPLACED_FRAGMENT` 90 → 0，`SCALE_CHANGE_FRAGMENT` 49 → 0，`LOW_CONFIDENCE_PLACEMENT` 693 → 275，reveal 能执行，主画布 5801×5000。31 组非相邻帧的独立 SIFT 长基线全部落在同一画布，位置差 median 1.49、p95 3.42、max 3.57 px；合法地理视窗的透明缺漏为 0。八段 public 的像素与瓦片证据和原算法完全相同。

### Reveal：选源与遮挡判断

追踪修好后，地图上的大面积缺字（Memorial、Columbia 等）主要是选源问题，不是几何问题：固定位姿后，标签在多张原始帧里都完整清楚，成品却混用了淡出中的帧和更早的片段。

- **先找变动核心再分配静态边界。** 原算法先膨胀变动块再求连通，静态边界把不同物件串在一起：Columbia 所在的分量有 1,499 块，真正变动的只有 385 块，最大的连通变动核心只有 52 块。这种群组几乎不可能被同一帧完整看到。只把「九成覆盖就更新」改成 100% 而不修分组，会在地图另一处切字。
- **相位分组只用于确实超出视窗的核心。** 全局相位版通过了自动测试，却在 test_6 标题下新增白色碎片，并把边缘地标图示改选成半幅绘制的帧；两个生成反例分别留下 1,536／1,024 个错像素。最终只在变动核心跨度确实大于观察视窗时才按相位分组。
- **遮挡分类的三种错误。** 模板用亮度挑稳定像素、定位却要求 RGB 接近，半透明控件随背景变色就漏判（改为有结构的模板比亮度值与形状，纯色模板仍比 RGB）。相位与配准误差会降低协方差，不能当成透光衰减（要求真实的对比度下降，或重复、有方向且超出噪声的亮度偏移）。参照本身是噪声时不能用回归斜率（test_7 的干净白边曾被当成不透明覆盖，并使干净的第 98 帧得 tier 2、模糊的第 111 帧得 tier 3）。
- **静态块不能被弱边缘过早永久锁定。** test_6 的 Safari 网址胶囊细边差值约 46，刚好低于 48 级离群门槛，区块在第 114 帧就成为 `Coherent`，后面的干净帧不再参与；修复用 3×3 世界格邻域检查局部结构。后来又在同一段 `[320,3380,160,28]` 发现 24 个来自第 115 帧的控件像素：相位相容只代表可用，需要另一个实际观察佐证才永久锁定。
- **可观察物件要同一时刻。** 生成的 `document-slider` 是 140×12 的长条，两端变化、中间不变；两个变动核心各自完整，却选了不同帧，输出被拉成 190 px 宽（2,280 像素，任何输入帧都只有 1,680）。逐像素真值查不出这种错，因为每个像素都曾出现过。修复只在当前帧实际完整观察了相邻群组时才合并时刻；合并后的群组不能降低成员已有时刻的等级，否则第一次共同出现时的单帧闪烁会被选入。2026-10-17 的 review 又发现判断能否合并的 `witness` 比 `emit` 更严，会让较弱的初期参照否决更干净的观察：test_3 有一张缩图因此被拆成第 840／842 帧三块，对齐后整张取自第 840 帧。
- **多色长轨道里的控件实例。** test_1 右缘的滚动条残影有 320 个误差 > 25 的像素，全部由 `Fallback` 写入：模型把固定边框和移动滑块平均成一个 25×1037 cells 的长物件。最终方案追踪实际连通元件，要求三次唯一匹配、运动不同于页面，并且按页面运动推算的位置可观察、实际影像反驳这个解释（少了这一条，重复的正文底线会被当成同一元件，test_6 多出 567 处改动）。test_1 的该区 320 → 8。

### 性能

- **packed HDR 色码查表。** 每次转色先为 256 或 1024 种通道色码算好原有的 EOTF 插值，矩阵运算次序、sRGB 映射和高亮计数不变；YUV 矩阵后的连续值仍走原插值。三种 Wasm 核心对 PQ／HLG 穷举全部 16,777,216 组 RGB8，另测 1,010,240 组 RGB10A2，结果一致（这些检查没有进仓库）。完整 test_5 为 292.69 → 138.29 秒，两边处理同样的 1,852 帧、12,760 次转色，PNG 一致。
- **translation audit 共用准备。** 同一图像对的平滑只做一次。test_2 同一输入的 audit 子步骤 370 → 275 ms，约省 95 ms，不是整条管线快 26%。

### 合成真值：逐帧视口

`Layer.viewports` 把「实际可视范围」和「页面平移」分开描述。`toolbar-collapse` 的 51 帧输入与改动前逐字节相同，只改变验证器的预期。新增的反例是同一段 51 帧录屏的另一种解释：初始顶栏其实是文件自己的标题，往下滚动后变成 sticky header。现行输出在这种解释下 missing、invented、mismatched 都为 0；若无条件回填视口，第一种解释的 invented 48,360 → 0，第二种却会丢掉 48,360 个只被观察过一次的标题像素。

## 排除的路线

| 路线                                                                 | 排除原因                                                                                                                      |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 把同像素的负面证据放在两道 gate 之前（通用降级）                     | phone 可恢复污染 1,249 → 1,331，超过棘轮；dynamic 的 provisional 0 → 795                                                      |
| descriptor 通用剪枝                                                  | 真实特征上 matching kernel 慢 1.51／1.93 倍，只有全重复特征才变快                                                             |
| 无条件回填视口                                                       | 和 sticky 文件标题的录屏无法区分，会删掉 48,360 个唯一观察的像素                                                              |
| 延后投票、放宽边界投票                                               | 有些位置在整段录屏都没有合格的共同可见观察；中心格加遮罩搜索使 phone 可修复污染 1,127 → 1,175                                 |
| 整条轨道降为 fringe、整个物件的多色 key、按颜色限制横向范围          | 分别在 test_6 新增蓝色方块、在 test_1 留下黑色缺口（误差像素 381／389，当时为 320）                                           |
| 全局相位分组、父／子时刻锁定、局部带上下文补写                       | test_6 新增白色碎片、地标图示选到半幅帧、中间留下拼缝                                                                         |
| 不完整群组：完全停用、核心与上下文分开写、全局或逐块局部质量排序     | 分别使破字回来、切碎道路、让早期小片冻结其他区域、切开标签                                                                    |
| 无条件偏好中央观察；按中央程度选整块 veil 来源                       | `chrome-everything` 多 85 个游标污染像素；河面误差 > 12 的像素 1,548 → 2,042                                                  |
| 任意把 fallback 升为整块来源                                         | 地图细路新增断点；只看单块平坦也挡不住移到边界外的细线                                                                        |

| 稀疏画布架构                                                         | 八段 public 与完整地图都没有因容量跳过 reveal，它不是这批残影的原因                                                           |

## 仍未解决

- **细微几何误差。** 地图仍有约 3–4 px 的长距离误差（p95 Chrome 3.416、WebKit 3.635 px），会影响细字和道路的小接缝。可靠的长距离细配准可能有用，但这一轮没有足够的约束支撑整条路径校正。
- **控件残影与超出视窗的动态物件。** 地图外缘仍有部分旧标签和控件残留，test_3 仍有原 main 就存在的文字横断。从未被完整观察过的动态内容，不能靠多数决或局部质量排序凑出正确版本。
- **issues。** #1（时变视口）和 #2（边界帧的唯一干净观察）仍 open，部分位置已改善；#4 的 24 组扩充重现在原 main 和新版都通过，但缺少原始输入，不能算修好；#5 未涉及；#7 的这段 Apple Maps 已从 140 片变为一张图，Google Maps 和缩放、旋转仍未验证。
- **平台。** 只在 macOS 的 Chrome、Playwright WebKit 上做了完整对照，真 Safari 只跑了 test_7。Firefox 158 不支持这批 HEVC（`UNSUPPORTED_CODEC`）。Windows、Android、iOS 真机没有测。原 main 的 test_4 曾在渲染第 1,720 帧时触发 `DECODER_STALLED`，原因没有查清。
